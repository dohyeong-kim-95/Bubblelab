# lesson_learned — 파일럿에서 실측으로 배운 것

2026-07-31 파일럿(rabbit 캐릭터, 시트 1 + 컷 2회 + 실패 1프레임, 총 ≈$1)에서
배운 것만 적는다. 방법론 전반은 `SKILL.md`, 완료 조건은 `goal.md`.
**다음 반복 전에 이 파일부터 읽고, 반복이 끝나면 여기에 추가한다.**

## 인프라에서 배운 것

1. **Cloudflare Workers에서 Gemini 이미지 생성은 지역 차단에 걸린다.**
   `FAILED_PRECONDITION: User location is not supported` — 워커의 이그레스
   IP가 미지원 지역으로 geolocate 되는 경우이며 우리가 제어할 수 없다.
   같은 키로 팟캐스트(텍스트·TTS, cron 실행)는 통과한다 — 실행 시점의
   데이터센터가 다르고 이미지 모델의 지역 제한이 더 엄격하다.
   → **생성 실행처는 GitHub Actions 러너(미국 IP)가 기본.** 잡 파일
   (`_src/emoticon/job.json`) 커밋으로 트리거한다.
2. **Worker secret은 어디서도 읽어올 수 없다** (write-only). 다른 실행 환경
   (Actions·로컬)에서 쓰려면 같은 값을 그 환경의 secret으로 한 번 더
   등록해야 한다. 이건 우회가 아니라 구조다.
3. **세션의 GitHub 토큰으로는 workflow_dispatch를 못 부른다**(actions:write
   없음). push 트리거(잡 파일 패턴)가 에이전트 친화적 우회다.
4. **산출물을 리포에 커밋하는 구조가 반복 속도를 결정한다.** 에이전트가
   pull → 이미지 확인 → 프롬프트 수정 → 재잡 커밋의 루프를 사람 개입 없이
   돈다. 실패해도 부분 산출물(frames-raw)을 커밋해야 원인을 이미지로 볼 수
   있다 (`if: always()`).

## 생성 품질에서 배운 것

5. **배경 색 지시는 레퍼런스 이미지에 진다.** "초록 배경(#00FF00)"이라고
   써도 흰 배경 시트를 레퍼런스로 주면 흰 배경으로 그린다. 싸우지 말 것 —
   흰 배경으로 생성하고 누끼는 모서리 색 자동 판별(autoCutout: 초록이면
   크로마키, 흰색이면 sticker-pack의 플러드필)로 처리한다.
6. **캐릭터 일관성은 생각보다 잘 나온다.** 시트 1장 + 첫 프레임 + 직전
   프레임을 레퍼런스로 주면 12프레임 전부 같은 캐릭터가 유지됐다(귀·볼터치·
   선 굵기·비율). goal.md 기준 1은 현재 전략으로 근접했다.
7. **시간적 연속성이 진짜 병목이다.** "프레임 i/N" 지시만으로는 모델이
   프레임마다 독립적인 포즈를 그린다(팔이 좌우로 바뀌고 크기가 출렁임 —
   1차 루프 diff 34%, 재생하면 보일링).
8. **포즈 스크립트(프레임당 포즈 문장 1개)가 즉효였다.** 동작 진행을
   "2번: 오른팔 어깨 높이, 3번: 머리 위로 쭉…"으로 고정하니 동작 아크가
   생기고 루프 diff 34→21%. `cut --poses` / 잡 파일 `poses` 배열.
9. **"오른팔" 같은 좌우 표현은 캐릭터 기준/화면 기준이 섞인다.** 프레임마다
   해석이 달라져 드는 팔이 좌우로 오갔다. → 포즈 문장은 **"화면 기준
   오른쪽"**처럼 시점을 명시할 것. (다음 반복에서 검증 예정)
10. **12fps·12프레임은 아직 인접 프레임 변화가 크다**(최대 diff 32%).
    다음 실험: 8프레임 @8fps — 변화 폭과 비용을 같이 줄인다. 사람 애니메이션
    기법(2s 작화 등)은 `animation-techniques.md` 참고.
11. **모션 라인(속도선)은 지시 없이도 그려 넣는데, 이모티콘에선 오히려
    자연스럽다.** 금지하지 않는다. 단 프레임 간 위치가 널뛰면 소음이 된다.
12. **(3R 스텝1) 순차 생성은 프롬프트 개선으로 포화됐다.** hello3(화면 기준
    좌우 표현 + 8프레임 @8fps): 루프 diff 21→16.4%로 개선됐지만 **"화면
    기준"으로도 팔 좌우 고정은 실패**(8프레임 안에서도 드는 팔이 오감),
    인접 diff 34.4%로 여전히 컸다. 결론: 포즈 문장 수정은 한계 — 남은
    이득은 구조 전환(pose-to-pose·유니크 축소·조립)에서 나온다.

## 파이프라인 구현에서 배운 것 (3R 스텝2 — keys 모드)

13. **홀드·ease는 프레임 복제가 아니라 APNG 프레임별 delay로 구현한다.**
    fcTL의 delay_num이 프레임마다 다를 수 있어서(0.001초 단위) "키 3프레임
    홀드"가 파일 용량 증가 없이 표현된다 — 사람 애니메이터의 타이밍
    차트가 인코딩 레벨에 그대로 있는 셈. `encodeApng(frames, { delaysMs })`.
14. **핑퐁 역순은 타임라인으로만 전개하고 유니크 프레임은 한 번만
    저장한다.** APNG에 프레임 재사용 참조는 없어 인코딩 시 역순 프레임이
    다시 들어가지만(용량 ~1.5배), 리포·히스토리에는 유니크만 남는다.
    끄덕·두근 같은 왕복 동작은 생성비가 절반이 된다.
15. **브레이크다운은 v1에서 키 쌍당 1장(중간)만.** favor(70:30)·2장
    브레이크다운은 중간 1장이 실생성으로 검증된 뒤에 붙인다 — 검증 안 된
    자유도를 미리 늘리지 않는다.
16. **잡 파일 스키마가 곧 기획서다.** keys 모드의 잡:
    `{"step":"cut","cut_id":"nod","prompt":"동작","keys":[{"pose":"...","hold":2},...],
    "breakdowns":1,"assembly":"pingpong"}` — 애니메이터의 "키 포즈 + 타이밍
    차트 + 조립 규칙"이 그대로 JSON이 됐다. 실생성 검증은 스텝3에서.

## 3R 스텝3 — keys 모드 실생성 검증 (표준 방식 확정)

17. **픽셀 diff만으로는 품질을 판정할 수 없다.** 인접 diff는 "의도한 큰
    움직임"과 "원치 않는 떨림"을 구분하지 못한다(유니크 3장으로 끄덕임
    전체를 표현하면 한 걸음이 클 수밖에 없다). **캐릭터 경계 상자 높이의
    변동폭(scaleDrift)**을 추가하니 결함만 분리돼 보였다 — 재생 시 캐릭터가
    커졌다 작아지는 펄스가 진짜 결함이다. build가 셋 다 리포트한다.
18. **keys 모드가 1/3 비용으로 순차 생성 최고 기록과 같은 안정성을 냈다.**

    | 컷 | 방식 | 생성 | 크기 드리프트 | 인접 diff |
    |---|---|---|---|---|
    | hello | 순차 | 12 | 16.0% ⚠ | 34.6% |
    | hello2 | 순차+포즈 | 12 | 18.6% ⚠ | 32.4% |
    | hello3 | 순차+화면기준 | 8 | 5.4% | 34.4% |
    | nod | **keys** | **3** | 5.8% | 37.1% |
    | heart | **keys+몸고정** | **3** | **0.0%** | **3.9%** |

19. **브레이크다운(양쪽 키를 레퍼런스로 중간 생성)은 실제로 작동한다.**
    nod의 가운데 프레임이 고개가 절반쯤 기울어진 진짜 중간 자세로 나왔다.
    스텝2 설계의 핵심 가정이 검증됐다.
20. **결정적 발견 — "몸 고정 + 일부만 변화"가 압도적으로 안정적이다.**
    heart(몸·크기·위치를 지시로 고정하고 눈·하트만 변화)는 드리프트 0.0%,
    인접 diff 3.9%로 다른 컷과 차원이 다르다. 이건 리서치의 **부분
    애니메이션(리미티드 기법)** 원칙 그대로다 —
    `animation-techniques.md` §3. **표준 방식으로 확정한다.**
21. **대신 몸을 고정하면 동작 진폭이 작아진다.** heart는 "하트가 훨씬
    커진다"는 지시를 약하게만 따랐다. 앞으로 포즈 문장에서 **변하는 요소만
    극단적으로 과장**(12원칙 exaggeration)하고 나머지는 "identical" 수준으로
    못박는 대비 구조를 쓴다.
22. **포즈 준수는 텍스트의 한계가 있다.** nod 키2는 "팔은 몸 옆에"를
    어기고 팔을 얼굴로 올렸다. 좌우 지정 실패(§9·§12)와 같은 뿌리 —
    텍스트로 자세를 못박는 것 자체가 한계이며, 다음 후보는 스켈레톤
    조건화(`pose-conditioning.md` 리서치 결과)다.

## 4R — 스켈레톤 조건화 게이트 (실패, 그러나 큰 부산물)

23. **레퍼런스가 "시트"면 모델이 시트를 복제한다.** lrtest 1차에서 스켈레톤을
    무시하고 **캐릭터 시트 전체(다중 뷰 + 표정 아이콘)를 재생산**했다
    (드리프트 74%). "Image 1의 캐릭터를 그려라"가 여러 컷이 든 시트 앞에서
    "시트를 복제하라"로 끌린 것. → `--ref`로 **단일 정면 컷**을 주고
    "한 캐릭터·한 포즈만, 시트/그리드/다중 뷰 금지"를 명시하니
    **드리프트 74.2% → 0.6%**. 스켈레톤과 무관하게 **모든 모드에 적용할
    가치가 있는 발견**이다 (시트는 캐릭터 설계용, 생성 레퍼런스는 단일 컷).
24. **그럼에도 포즈 게이트는 실패했다.** lrtest2에서 4개 포즈(차렷/오른팔/
    왼팔/양팔)가 **구분되게 재현되지 않았고**, 좌우도 지시대로 가지 않았다.
    일부 프레임엔 **스켈레톤 색이 그림에 새어 들어왔다**(금지 지시 위반).
25. **원인 가설 — 체형 불일치.** 우리 토끼는 팔이 몇 px짜리 뭉툭한 돌기다.
    인간형 스켈레톤의 "팔을 90도 든다"를 매핑할 대상 자체가 없다. DisPose가
    지적한 **"체형이 크게 다를 때 조건 신호가 품질을 훼손한다"**가 그대로
    나타났다. 스켈레톤 조건화는 **팔다리가 실재하는 캐릭터**에서 값어치가
    있고, 극단 치비에는 부적합할 수 있다.
26. **따라서 표준은 여전히 §20(keys + 몸 고정)이다.** 다만 §23의 단일 컷
    레퍼런스를 keys 모드에도 적용해 볼 값어치가 있다(현재 nod 드리프트 5.8%).

## 품질 게이트 (지표를 판정으로 바꾸기)

27. **경고만 찍고 exit 0으로 끝나면 게이트가 아니다.** build가 드리프트·정지
    경고를 내고도 성공으로 끝나서 불량이 Actions "성공"으로 커밋될 수 있었다.
    → build가 `report.json`을 남기고 `check --profile`이 판정해 **FAIL이면
    exit 1**. 인접 diff는 **최대값만이 아니라 전 구간을 저장**해야 어느
    프레임이 튀었는지 되짚고 redo를 추천할 수 있다.
28. **Hard와 Soft를 나눠야 한다.** 규격·구조·드리프트·누끼 실패는 동작 크기와
    무관한 결함이라 자동 실패시켜도 안전하다. 반면 인접 diff·움직임·루프
    이음새는 **동작이 클수록 같이 커지는 값**이라 단일 임계값으로 실패시키면
    잘 만든 큰 동작을 죽인다(nod: 인접 37%가 정상). 경고와 추천만 한다.
29. **루프는 절대값으로 판정하면 안 된다.** 핑퐁은 마지막→첫 전환이 원래 한
    걸음 차이라 loopDiff가 크게 나오는 게 정상이다. **인접 diff 중앙값 대비
    비율(seamRatio)**로 봐야 오탐이 없다.
30. **정지 임계값 실측 보정**: heart 3.8%는 눈으로도 정지, 그다음으로 낮은
    lrtest2가 15%. 그 사이인 8%를 기준으로 잡았다(표본이 적어 재조정 대상).
    적용 결과가 육안 판정과 일치한다 — hello/hello2/lrtest는 드리프트로 FAIL,
    heart는 정지로 REVIEW, hello3/nod/lrtest2는 PASS.
31. **게이트는 기술 결함만 잡는다.** lrtest2는 포즈 지시를 전부 어겼는데도
    PASS다("지시한 대로 움직였는가"는 픽셀 지표가 볼 수 없다). 사람 검수가
    여전히 필요하고, goal.md의 일반화 게이트가 그 자리다.

## 프롬프트 규약 실검증 (nod5 — 부정어 제거 + POSE 우선)

32. **규약의 두 수정이 각각 겨냥한 결함을 실제로 없앴다.** 같은 끄덕임 컷을
    새 규약으로만 다시 뽑았다(3장, $0.12).
    - **POSE를 IDENTITY 앞으로** → 움직임 복구. motionMean 12.4%(nod3) →
      8.6%(nod4) → **19.0%(nod5)**. 발은 바닥에 붙고 머리·몸이 아래로 내려간다.
      nod3·nod4가 얼어붙은 원인은 프롬프트 **내용**이 아니라 **순서**였다.
    - **부정어 제거** → 귀 3개 재현 안 됨. nod2의 세 번째 귀는
      `never more than two ears`가 부른 것이었다(§부정어는 대상을 소환한다).
33. **열린 형용사는 상한 없는 지시로 읽힌다.** `the body spreads wider as it
    compresses`가 가로 +33%(402→535px)를 만들었다. 부피 보존이면 세로 −18%에
    대해 +22%여야 한다. → **배율을 숫자로 못박는다**: "0.92배 높이, 1.08배 폭".
34. **부위의 "움직임"을 쓰면 그 부위의 종류가 바뀔 수 있다.**
    `both ears swing forward over the forehead` → 선 귀가 **처진 귀(lop)**로
    교체됐다. bbox 상단이 102px 사라진 원인이 이것이고, 몸통 스쿼시가 아니다.
    → 움직임에 **밑동·길이 고정을 긍정문으로 동반**한다: "밑동은 머리 위에
    있고 길이는 그대로, 끝 1/3만 앞으로 기운다".
35. **`scaleDrift`(bbox 세로)는 세로 동작과 구조적으로 충돌한다.** 끄덕임은
    실루엣이 짧아지는 게 정상이라 정당한 동작도 드리프트로 잡힌다(반대로 wave는
    가로가 변한다). 지표의 의도는 "그림이 통째로 커졌다 작아졌다 하는가"이므로
    **동작축의 수직 방향**에서 재는 게 맞다. 단, nod5는 가로로 재도 24.9%라
    **어느 기준으로도 불합격** — 이번 실패를 통과시키려고 지표를 고치는 게
    아님을 확인하고 나서 손댄다.
36. **POSE 블록에 "부위가 어디에 머무는지"를 긍정문으로 넣는 건 규약 위반이
    아니다.** nod5는 invariants에 "two arms"가 있었는데도 앞발이 배 위로
    접히고 아래 양옆에 덩어리가 생겼다. 부품 **개수**는 CANON이 지키지만
    **위치**는 POSE에서 말해야 한다("both short arms stay hanging at the sides").

## 사람 검수 13건이 알려준 것 (첫 일괄 피드백)

37. **에이전트 판정과 사람 판정이 크게 어긋난다.** 내가 실패로 분류한 nod9를
    사람은 "아주 맘에 듭니다"로 평가했다. 나는 **얼굴이 안 내려갔다**는 한 축만
    보고 있었고, 사람은 **그림이 깨끗하고 표정이 살아 있는지**를 봤다.
    지표를 늘리기 전에 **무엇을 보고 있는지**부터 사람과 맞춰야 한다.
38. **1위 결함은 "여분 사지"이고, 나는 이걸 육안으로 계속 놓친다.**
    13건 중 5건 — nod2 귀 3개, nod3·nod4 귀 4개(위로 선 귀 2개 + 옆으로 처진
    귀 2개), nod5 손 4개, nod11 팔 4개. 드리프트·움직임 지표로는 **전혀** 안
    잡히고, 내가 프레임을 봐도 반복해서 못 봤다. **자동 검사가 필요한 1순위.**
39. **반복해서 나오는 요청은 "프레임을 늘려라"다.** nod6 "프레임이 적음",
    nod9 "프레임만 늘리면 두리 이모티콘으로 쓸 수 있을지도", nod11 "표정의
    부드러움은 프레임을 늘리면 해결". 동시에 nod10에는 "프레임 낭비가 심하다,
    같은 내용을 **8프레임(편도)** 로 가능". → **편도 8장이 기준선.**
40. **얼굴을 너무 내리면 불합격이다.** nod10 "얼굴이 턱밑까지 내려왔다".
    리그 최대 이동 69px은 과했고, 40px 쪽이 맞았다.
41. **끄덕임과 눈깜빡임을 사람은 바로 구분한다.** nod11에 "끄덕임보다는
    표정바뀜(깜빡이)에 가깝다" — 내 판정과 일치한다. 즉 지금까지의 nod 작업은
    **사실상 눈깜빡임을 만들고 있었다.**

## 부품 개수 자동 검사 — 두 설계 모두 실패 (재시도 금지)

42. **머리 위 가로 스캔으로 귀 세기: 실패.** 외곽선 그림이라 색으로 판정하면
    획을 센다(귀 2개 → run 6개: 외곽선·분홍·외곽선 ×2). 누끼 알파로 도형을
    세면 그건 맞지만, **처진 귀는 머리 옆에 붙어 있어 머리 위 구간에 안 잡힌다.**
    nod3·nod4의 귀 4개를 전부 "2개"로 통과시켰다.
43. **레퍼런스 실루엣 밖 면적 비율: 실패.** 큰 붕괴는 잡는다(nod2 21.6%,
    nod5 23~26%). 그러나 **정상적인 동작과 구분되지 않고**(wave가 팔을 들면
    7.2%) nod3·nod4의 귀 4개는 1.6~3.5%로 그 아래이며, nod11의 팔 4개는
    **0.1%로 신호가 아예 없다**(여분 팔이 몸 실루엣 안에 그려짐).
44. **→ 기하로는 안 된다. 부품 세기는 비전 검사로 간다.** "이 캐릭터의 귀는
    몇 개인가"는 VLM이 잘하는 일이고, 이미지 1장당 텍스트 응답이라 생성
    ($0.039)보다 훨씬 싸다. 생성 직후 프레임마다 물어보고 기대치와 다르면
    hard 실패시킨다.

## 비전 부품 검사 — 13컷 82프레임 실측 (채택)

45. **비전 검사는 귀 결함을 100% 잡았다.** 사람이 지적한 3건을 개수까지 정확히
    맞혔다 — nod2 귀 3개, nod3·nod4 귀 4개. 13컷 전체에서 **귀 오탐 0건.**
    기하 검출 두 설계가 전부 실패한 자리를 그대로 메운다(§42~43).
46. **팔은 4건 중 1건을 놓쳤다.** nod11의 팔 4개는 **사람이 지목한 프레임까지
    정확히** 짚었지만, nod5의 손 4개는 못 봤다. 초과 검출은 믿을 만하고
    민감도는 완전하지 않다 — 사람 검수를 대체하지 못한다.
47. **초과와 부족은 성격이 완전히 다르다.** 초과(귀 3·4개, 팔 4개)는 **전부
    진짜 결함**이었고, 부족(팔 1개)은 **전부 겹침**이었다 — wave가 팔을 들어
    몸에 겹친 프레임을 "팔 1개"로 셌다. → **초과만 hard, 부족은 soft.**
    이 분리로 13컷에서 잘못된 자동 실패가 0건이 된다.
48. **모델 이름을 상수로 박으면 안 된다.** `gemini-2.5-flash`가 "신규 사용자
    에게 더 이상 제공되지 않는다"는 404로 죽었다. ListModels로 받아
    generateContent 지원 모델 중에서 고른다(현재 선택: gemini-3.6-flash).
49. **부품 검사는 컷당 몇 초·몇 원이다.** 82프레임 전수 검사가 1분 안에 끝났다.
    이미지 생성($0.039/장)과 자릿수가 다르므로 **모든 컷에 기본으로 돌린다.**
