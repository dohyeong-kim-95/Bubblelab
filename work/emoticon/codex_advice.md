# Codex advice — CLI 게이트 우선 원칙

이 문서는 `work/emoticon`을 이어서 작업하는 Codex를 위한 실행 지침이다.
현재 개발 순서는 **CLI가 품질 게이트를 통과한 뒤 브라우저가 따라가는 방식**이다.
브라우저가 CLI보다 뒤처진 것은 의도된 상태이므로, CLI 게이트가 통과하기 전에는
브라우저 기능 동기화나 UI 확장을 우선하지 않는다.

관련 기준은 다음 문서를 함께 따른다.

- `goal.md`: 최종 완료 조건
- `lesson_learned.md`: 실험으로 확인된 사실
- `animation-techniques.md`: pose-to-pose·리미티드 애니메이션 원칙
- `pose-conditioning.md`: 스켈레톤 조건화 연구와 실패 범위
- `_infra/emoticon.mjs`: 현재 CLI 구현

## 1. 현재 판정

CLI는 **파이프라인 실행 게이트는 통과했지만 품질 게이트는 아직 통과하지
못했다.** 구체적으로는 다음과 같다.

| 게이트 | 상태 | 근거 |
|---|---:|---|
| 테스트·인프라 | 통과 | 이모티콘 전용 테스트 18개 + 모노레포 전체 검증 |
| 시트 → 컷 → 누끼 → APNG | 통과 | mock E2E 검증 완료 |
| keys → breakdown → hold/pingpong | 통과 | 생성·조립·재빌드 구현 완료 |
| 특정 프레임 `redo` | 통과 | keys 모드에서 동작 |
| 자동 품질 판정 | 미통과 | 현재 `build`는 경고 후에도 성공 종료 |
| 여러 동작으로 일반화 | 미통과 | `heart` 한 사례만 안정적 |
| 2초 마스터 | 미통과 | 현재 실험 산출물은 0.58~1.00초 |
| 파일럿 4~6종 | 미통과 | 서로 다른 동작 유형의 반복 성공이 아직 없음 |

2026-07-31 현재 산출물을 최신 지표로 다시 빌드한 값은 아래와 같다.

| 컷 | 루프 diff | 인접 diff 최대 | 크기 드리프트 | 움직임 평균 | 판정 |
|---|---:|---:|---:|---:|---|
| `hello` | 34.0% | 34.6% | 16.0% | 25.0% | 실패 |
| `hello2` | 21.1% | 32.4% | 18.6% | 16.1% | 실패 |
| `hello3` | 16.4% | 34.4% | 5.4% | 19.0% | 일부 개선 |
| `nod` | 28.7% | 37.1% | 5.8% | 40.5% | 동작은 크지만 불안정 |
| `heart` | 2.4% | 3.9% | 0.0% | 3.8% | 품질지표 통과, 동작 진폭 부족 |
| `lrtest` | 26.1% | 72.2% | 74.2% | 38.9% | 실패 |
| `lrtest2` | 6.0% | 20.5% | 0.6% | 15.0% | 수치는 근접, 포즈 준수 실패 |

`heart`는 성공 공식의 증거지만 0.58초·4타임라인 프레임이므로 `goal.md`의
2초 기준까지 통과한 것은 아니다. 현재 단계는 **성공 레시피 하나를 발견한
상태**로 판단한다.

### 1.1 구현된 실행 안전성 기반

품질 게이트 작업에 앞서, 비용이 드는 CLI 반복을 안전하고 재현 가능하게 만드는
기반은 구현됐다.

- `plan`: 파일/API 무변경 상태로 호출 수·재사용 수·비용·출력 시간을 계산
- `--max-calls`, `--max-cost`: 실행 전과 자동 재시도 중 동일한 예산 상한 적용
- `--resume`: spec·시트·레퍼런스 SHA-256이 일치하는 정상 raw만 재사용
- 원자적 저장: 이미지·메타·APNG를 임시 파일에 완성한 뒤 rename
- `cut.json` schema v2: CLI·프롬프트 버전, 입력 해시, 프로바이더, 커밋,
  실행별 상태·시각·호출 수와 누적 비용 기록
- `--force`: 컷 디렉터리를 먼저 교체해 이전 실행의 오래된 프레임 제거
- Actions: 생성 전에 `_infra/*.test.mjs` 전체 테스트와 루트 빌드 수행

이 항목들은 **실행·재현성 게이트**를 통과시킨 것이며, 아래의 자동 품질 판정
게이트를 통과했다는 뜻은 아니다. 다음 구현 우선순위는 그대로 `report.json`과
`check --profile`이다.

## 2. 가장 먼저 고칠 것 — 게이트를 실제 게이트로 만든다

현재 `build`는 루프·인접 변화·크기 드리프트·움직임 부족 경고가 발생해도
exit code 0으로 끝난다. `check`는 APNG 구조와 크기·프레임·시간만 확인한다.
따라서 품질 불량 산출물도 Actions 성공으로 처리되고 커밋될 수 있다.

목표 흐름은 다음과 같다.

```text
build → report.json 생성
      ↓
check --profile <프로필>
      ├─ PASS   → 승인 후보
      ├─ REVIEW → 사람 검수 필요
      └─ FAIL   → non-zero exit, Actions 실패
```

### Hard gate

다음 항목은 자동 실패시켜도 된다.

- 빈 프레임 또는 누끼 실패
- 출력 크기·프레임 수·재생시간·용량 위반
- APNG 구조 또는 애니메이션 청크 오류
- 프레임 간 캐릭터 크기 드리프트 과다
- 컷이 참조한 캐릭터 시트와 현재 시트의 해시 불일치
- 플랫폼 프로필의 재생시간·반복 횟수 규칙 위반

### Soft gate

다음 항목은 동작 자체가 클 때도 증가하므로 단일 임계값으로 실패시키지 않는다.

- 인접 프레임 diff
- 정렬 후 움직임 평균·최대
- 루프 경계 diff
- 동작 진폭
- 색상·세부 묘사 변화

특히 `loopDiff`의 절대값만으로 루프를 판정하지 않는다. 핑퐁 타임라인은
마지막 프레임과 첫 프레임이 달라도 그 전환이 정상 인접 전환과 비슷하면
자연스러울 수 있다. 루프 경계를 판정할 때는 다음과 같은 상대 지표를 우선한다.

```text
seamDiff / 일반 인접 diff의 중앙값 또는 상위 분위수
```

## 3. 구현 우선순위

### 3.1 `report.json`을 저장한다

`build`의 콘솔 출력만 남기지 말고 컷별 기계 판독 가능한 리포트를 저장한다.

```json
{
  "duration": 2.0,
  "uniqueFrames": 4,
  "timelineFrames": 12,
  "loopDiff": 0.024,
  "adjacentDiffs": [0.039, 0.031, 0.039],
  "scaleDrift": 0.0,
  "motionMean": 0.038,
  "motionMax": 0.045,
  "sheetHash": "...",
  "profile": "master-2s",
  "verdict": "review"
}
```

최대 인접 diff만 기록하지 말고 모든 인접 구간 값을 저장한다. 그래야
`redo`가 의심 프레임을 추천할 수 있다.

### 3.2 `check`가 판정하고 실패하도록 만든다

권장 인터페이스:

```bash
node _infra/emoticon.mjs check <작업폴더> <컷id> --profile master-2s
node _infra/emoticon.mjs check <작업폴더> <컷id> --profile line
```

- PASS: exit 0
- FAIL: exit 1
- REVIEW가 별도 exit code를 쓸지는 CI 처리 방식을 보고 결정
- `--json` 옵션으로 판정 결과를 stdout에 출력할 수 있게 한다

### 3.3 캐릭터 시트 버전을 고정한다

`cut.json`에 생성 당시의 `sheetHash`를 저장한다. 시트를 `--force`로 교체한 뒤
기존 컷과 새 컷이 한 팩에 섞이지 않도록, 빌드·체크 시 현재 시트 해시와 다르면
Hard fail한다.

### 3.4 keys 모드에 단일 캐릭터 레퍼런스를 적용한다

스켈레톤 실험에서 전체 시트 대신 단일 정면 컷을 쓰자 크기 드리프트가
74.2%에서 0.6%로 줄었다. 이 발견을 실험 모드에만 두지 말고 표준인 keys
모드에서 검증한다.

다음 기본 조합을 우선 실험한다.

```text
keys + 몸 고정 + 변하는 요소만 과장 + 단일 정면 reference
```

`heart2`로 변화 요소의 진폭을 키우고, `nod2`로 몸을 고정한 채 고개만
변화시키는 실험을 먼저 한다.

### 3.5 재작업 대상을 CLI가 추천한다

`report.json`의 인접 구간·프레임별 경계 상자 값을 이용해 다음을 출력한다.

```text
REVIEW: 03→04 구간 변화가 전체 중앙값의 2.4배
REVIEW: 프레임 04 높이가 컷 중앙값보다 9.1% 큼
SUGGEST: emoticon.mjs redo <작업폴더> <컷id> 4
```

자동 `redo` 실행은 재시도 폭주를 막기 위해 나중에 고려하고, 우선 추천만 한다.

## 5. 당분간 우선하지 않을 것

- 브라우저 UI 동기화 및 기능 확장
- 극단적인 치비 캐릭터에 대한 스켈레톤 조건화 추가 연구
- 이미지·비디오 프로바이더 추가
- 16·24·32종 일괄 생성
- 품질 게이트 없이 프레임 수만 늘리는 실험

현재 병목은 모델 비용이나 생성 호출 수가 아니라 **CLI가 품질을 재현성 있게
판정하고 실패를 막는 능력**이다.

## 6. 테스트 요구사항

게이트 구현 시 최소한 다음 테스트를 추가한다.

- 경고 기준을 넘은 fixture가 `check`에서 실패하는지
- `report.json` 스키마와 값이 재빌드 후에도 결정적인지
- 시트 해시 불일치를 탐지하는지
- master-2s 재생시간을 강제하는지
- LINE 프로필의 시간·반복·프레임·용량 규칙을 강제하는지
- 핑퐁의 정상적인 마지막→첫 전환을 절대 `loopDiff`만으로 오탐하지 않는지
- 의심 프레임 추천이 실제 최대 이상 구간과 연결되는지

## 7. 운영상 주의

미출시 마켓 제출용 원본을 public 저장소에 커밋한 뒤 나중에 삭제하는 방식은
보호가 되지 않는다. 삭제 전 커밋의 Git 기록에 파일이 남기 때문이다. 파일럿
이후의 최종 원본·raw frame·제출본은 처음부터 private 저장소나 별도 스토리지에
보관하고, public 저장소에는 레시피·지표·필요한 리뷰용 자료만 남긴다.

`lesson_learned.md`의 실측 결과를 먼저 갱신하고, 그 결과가 우선순위를 바꾸면
