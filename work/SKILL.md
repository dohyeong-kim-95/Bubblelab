# SKILL — 섹션 페이징(풀페이지 스크롤) UI/UX

스크롤을 가로채 "제스처 하나 = 화면 한 장"으로 넘기는 패턴(풀페이지 스크롤,
scroll snap paging, 넓게는 scrolljacking)을 만들 때의 원칙 모음.
리서치(NN/g 등)와 이 리포에서 실제 구현·검증한 내용(daonfit 인트로,
work 메인)을 합쳐 정리했다. 다음에 같은 패턴을 만들 때 이 문서부터 읽는다.

## 0. 전제 — 기본값은 "쓰지 않는 것"

NN/g의 사용성 테스트 결론: 스크롤재킹은 **사용자 제어감·발견 가능성·주의·
효율·과업 성공**을 모두 위협한다. 사용자는 "입력한 만큼, 입력한 방향으로"
움직인다는 강한 멘탈 모델을 갖고 있어서, 이를 깨는 순간 기능적 가치가
없다면 브랜드 인상까지 깎인다.

**써도 되는 경우**: 순서가 있는 짧은 이야기(브랜드 인트로), 한 화면 단위로
완결되는 소수의 섹션(3~5장), 보는 것 자체가 목적인 연출. **피해야 하는
경우**: 읽는 콘텐츠(문서·블로그·긴 목록), 비교하며 오가는 화면, 폼.

## 1. 정지 상태는 항상 완결 화면이어야 한다

스크럽(스크롤 위치 = 애니메이션 진행률)만 있으면 사용자가 중간에 멈췄을 때
반쯤 조립된 깨진 화면이 남는다. 실제로 다온핏 인트로에서 첫 피드백이
"중간에 멈추면 깨져 있는 채로 멈춘다"였다.

- 모든 앵커는 **깨끗한 상태**가 되도록 타임라인을 앵커에 맞춰 설계한다
  (요소 조립·문구 전환이 앵커 지점 전에 끝나게).
- 제스처 밖 이동(스크롤바 드래그, 키보드, 관성 잔여)은 **idle 스냅**이
  수습한다: 멈춤 감지(우리 값 0.18초) 후 가까운 앵커로. 구간 진행 25%
  미만이면 이전, 이상이면 다음 앵커(단순 최근접보다 진행 방향을 존중).

## 2. 제스처 하나 = 정확히 한 장

- 전환 중 입력은 **삼킨다**(preventDefault, 전환은 끝까지 재생).
- 전환 완료 후 **관성 흡수 잠금**(우리 값 250ms) — 트랙패드 관성 꼬리가
  다음 장을 넘겨버리는 이중 넘김을 막는 핵심.
- 휠 delta는 `deltaMode`를 정규화한다(Firefox는 line 단위 ±3).
- 단, 사용자를 이기려 들지 말 것: **idle 스냅(수습용) 중에 제스처가 오면
  즉시 취소하고 양보**한다. 삼키는 것은 "사용자가 시작한 페이지 전환"뿐.

## 3. 방향 정책을 콘텐츠 성격으로 결정한다

- **내러티브형(다온핏 인트로)**: 이야기는 순방향만 의미가 있다. 앞으로는
  가볍게(터치 12px), **뒤로는 확실한 제스처만**(휠 300ms 누적 -80px,
  터치 48px) — 작은 흔들림으로 되돌아가지 않게. 완주 후에는 역재생을
  막고 마지막 완성 화면을 "맨 위"로 삼는다(재생은 새로고침).
- **콘텐츠형(work 메인)**: 페이지들이 대등한 정보라 앞뒤 **대칭**으로
  가볍게 오간다. 비대칭 임계값을 그대로 복사하면 답답해진다.

## 4. 페이지 = 뷰포트 계약

- 각 페이지 높이는 `100dvh`(iOS·안드로이드 주소창 접힘 대응 — `100vh`는
  모바일에서 튄다). 구형 폴백으로 `height:100vh; height:100dvh;` 순서.
- 페이지 콘텐츠는 한 화면에 들어가게 압축한다(썸네일 비율 조정, 여백 축소).
  들어가지 않는 콘텐츠는 페이징 대상에서 빼서 자유 스크롤 구간으로.
- **탈출구**: 마지막 앵커 아래(본문·footer)는 일반 스크롤로 풀어주고,
  그 경계 안으로 다시 올라오면 페이징이 다시 잡는다. 전체를 가두지 않는다.

## 5. 반응 속도와 이징

- 멈춤 감지·전환 시작이 느리면 "안 먹었나?"가 된다. 감지 0.18초,
  전환은 짧은 거리 0.26초부터 체감상 즉각적이다(처음 0.55초+최소 0.5초로
  잡았다가 "반응이 느리다" 피드백을 받고 줄였다).
- 이징은 **sine ease-in-out**(가속→감속)이 "페이지 넘김" 감각에 가장
  가깝다. ease-out은 시작이 급하고, cubic in-out은 중간이 과속한다.
  단, 연출이 주인공인 내러티브형에서는 클라이언트가 더 극적인 완급
  (느림→쇄도→느림)을 원할 수 있다 — 이때는 승수 시그모이드
  `t<.5 ? .5(2t)^k : 1-.5(2(1-t))^k`(k≈2.6)를 **연출이 실리는 장 하나에만**
  쓰고(다온핏은 조립 장), 단순 이동 장과 idle 수습 스냅은 sine으로 남겨
  놀라지 않게 한다(다온핏 2차 피드백 반영).
  전환 시간은 페이지별로 다르게 줄 수 있다(연출이 긴 장은 1.2초대,
  단순 이동은 0.5~0.7초).
- CSS `scroll-behavior: smooth`가 걸린 페이지에서 rAF로 프레임 단위
  `scrollTo`를 쓰면 겹쳐서 밀린다 — 트윈 동안 `scroll-behavior:auto`로
  임시 해제하고 끝나면 복원한다.

## 6. 접근성 — 선택이 아니라 요건

- `prefers-reduced-motion`은 WCAG 2.1 요건이다(미국 40세 이상 성인의
  최대 35%가 전정계 이상 경험). reduced-motion에서는 페이징·자동 스크롤을
  전부 끄고 **완성 상태 정지 렌더 또는 일반 스크롤**로 동작시킨다.
- 키보드(방향키·스페이스·Home/End)와 스크린리더 사용자는 가로채지 말고
  네이티브 스크롤을 허용한 뒤 idle 스냅으로만 수습한다.
- 터치 방향 판정 전(임계값 이하)에는 개입하지 않는다 — 네이티브 러버밴딩을
  유지해야 "화면이 고장났다"는 느낌이 없다.

## 7. 페이징은 CTA 도달을 늦춘다 — 고정 경로로 상쇄

페이징 장수만큼 핵심 행동(CTA)까지의 제스처 수가 늘어난다.
- 상단 고정 바에 핵심 CTA 상시 노출(work: "신규 의뢰하기").
- 또는 인트로 완료 시점부터 하단 고정 CTA 바(daonfit: 스토어 버튼 +
  신뢰 문구, 마지막 CTA 섹션에선 자동 숨김).
- 첫 화면에 핵심 메시지가 스크롤 전부터 보여야 한다(랜딩 UX 원칙과 동일).

## 8. 자동 테스트 없이 완성이라 하지 않는다

이 리포에서 쓰는 Playwright 검증 시나리오(전부 통과해야 배포):
1. 순방향 N틱 — 각 앵커에 정확히 정착 (y좌표 검증)
2. 마지막 장에서 순방향 — 자유 구간으로 풀림
3. 자유 구간에서 역방향 — 마지막 앵커로 복귀
4. 전환 중 연타 — 정확히 한 장만 이동
5. 작은 역방향 제스처 — (비대칭 정책일 때) 되돌아가지 않음
6. 확실한 역방향 — 한 장 뒤로
7. 스크롤바 드래그로 중간 방치 — idle 스냅이 앵커로 수습
8. 전환 중 사용자 입력 — (수습 스냅) 즉시 양보 / (페이지 전환) 삼킴
9. 멈춤→정착 소요 시간 실측 (감각 튜닝 근거)

## 9. 구현 방식 선택 — 네이티브 우선 (실측 교훈)

JS로 매 프레임 `scrollTo`를 호출하는 하이재킹은 **메인 스레드**에서 돌지만,
브라우저의 실제 스크롤은 **컴포지터 스레드**가 처리한다. 둘이 한 스크롤을
놓고 경합하면 특히 모바일에서 미세하게 떨리는(jank) 스크롤이 된다 —
work 메인 초기 구현에서 실제로 겪은 문제.

- **콘텐츠형 페이징은 CSS Scroll Snap이 기본값**:
  `scroll-snap-type: y mandatory` + 섹션 `scroll-snap-align: start` +
  `scroll-snap-stop: always`(플링 한 번에 여러 장 건너뛰기 방지),
  footer 등 자유 구간은 `scroll-snap-align: end`. GPU 가속·관성 통합·
  접근성이 전부 공짜고 JS 0줄이다. "모든 기기에서 좋은 스냅을 JS로
  재현하는 것은 사실상 불가능하다"는 것이 업계 중론.
- **JS 하이재킹이 정당화되는 유일한 경우**: 스크롤 진행률이 애니메이션
  타임라인을 구동해서 정착 지점을 코드가 정밀 제어해야 하는 내러티브형
  (다온핏 인트로). 이때도 터치 판정 전 구간은 네이티브에 맡긴다.
