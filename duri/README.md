# duri — 둘이서 쓰는 대화·사진 백업 (E2E)

상태: **개발 중**. duri.bubblelab.dev, 자체 비밀번호 게이트 뒤 비공개.

두 사람이 주고받은 대화와 사진이 **각자의 컴퓨터 디스크에 저절로 쌓이는** 기록
시스템. 여기에 둘만의 **공유 캘린더**와 다녀온 곳을 색칠하는 **지도**가 같은
앱 안에 탭으로 붙어 있다. 대화·사진 백업이 목적이라 bubblelab의 "토이 · 외부 서비스 금지" 원칙과
결이 다르므로, 랜딩·풀다운에 노출되지 않는 비공개 **전용 서브도메인**
`duri.bubblelab.dev`에 둔다(`_infra/build.mjs`의 `CONFIDENTIAL_SUBDOMAINS`).

원래 `work.bubblelab.dev/duri`(work 게이트 하위 경로)였으나, 앱화 후 work 홈
경유·주소 재입력이 번거로워 전용 서브도메인으로 승격했다. DuriDO는 호스트와
무관한 단일 인스턴스(`idFromName("main")`)라 승격으로 데이터가 옮겨가지 않는다.
복호화 키는 오리진별 IndexedDB에 있으므로 새 서브도메인에서 문구를 한 번 다시 입력한다.

## 게이트 (bl_duri, 1년 세션)

세션 쿠키는 **별도(`bl_duri`)이고 1년**이라, 설치형 앱은 최초 1회만 로그인하면
사실상 다시 묻지 않는다. 이 게이트는 E2E 암호 문구와 무관하다(문구는 앱 안에서
따로 받는다). 라우팅·게이트는 `_infra/worker.js`의 `handleDuriGate`·`duriPassword`.

- **비밀번호는 `DURI_PASSWORD` secret**을 쓴다. 없으면 `WORK_PASSWORD`로 폴백한다
  (설정 전에도 안 끊기게). `DURI_PASSWORD`를 설정하면 duri 접속 비번이 work과
  **완전히 독립**되고(work 로그인은 영향 없음), 파생 키가 바뀌어 **기존 bl_duri
  세션·싱크토큰(`DURI_SINK_SECRET` 미설정 시)은 무효화**된다 — 비번만 갈아도
  "접속 새로 시작"이 된다. 두 사람은 새 비번으로 다시 로그인한다.

## 방 초기화 (새로 시작)

앱 헤더의 **방초기화** 버튼 → `POST /_duri/reset`(소유자=`bl_duri` 세션만, 싱크
토큰으로는 불가). DuriDO가 서버 버퍼 전체 + 참조/고아 사진(R2) + 공유 캘린더
전체(`cal:*`)를 비우고 접속자에게
`reset`을 브로드캐스트해 양쪽 기기가 로컬 캐시를 지우고 재시작한다. **seq 카운터는
되감지 않고**(초기화 중 오프라인이던 기기의 커서 문제 방지) `ackSeq`를 `head`로
올려 "전부 소비됨"으로 만든다. **각자 PC 싱크 아카이브(원본)는 서버가 손대지
못하므로 그대로 남는다** — 정말로 지우려면 각 PC의 `DuriStorage/`를 직접 삭제.

## 구조 — 엣지는 중계소, 원본은 내 PC

- **Cloudflare(엣지) = 실시간 중계 + 임시 버퍼.** 영구 저장고가 아니다. 워커·DO·R2는
  전부 **E2E 암호블롭**만 다루므로 평문·키·신원을 알지 못한다.
- **데스크톱 싱크 = 진실의 원천.** 사용자 PC에서 상주하며 새 항목을 받아 로컬
  디스크에 기록하고 서버에 ack 한다 → 서버는 버퍼·R2에서 그 항목을 폐기한다.
  소스는 배포에서 제외되는 `_src/duri-sink/`(의존성 0, Node 20.10+). apk는 다음 단계.
- **설정은 앱 안에서**: ⚙️ → **💾 PC 백업 설정** → 🔑 싱크 토큰 발급 → 나온 JSON을
  PC의 `duri-sink.config.json` 에 붙여넣고 `bash install.sh`. 예전엔 개발자도구에서
  쿠키를 복사해 curl 을 쳐야 해서, 그 마찰 때문에 **정작 원본이 아무 데도 안 쌓이고
  있었다**(서버 버퍼 30일이 지나면 그대로 사라지는 상태였다).

## 앱화 (PWA)

홈 화면에 설치해 앱처럼 쓸 수 있다. `manifest.json` + `icon.svg`와 `<head>`의
apple/mobile 메타만으로 구성한 **최소 설치형 PWA**다. 최신 Chrome/Android는
매니페스트만으로 설치되고, iOS는 "홈 화면에 추가"로 담는다. 매니페스트는 duri
게이트 뒤라 `crossorigin="use-credentials"`로 받는다. `start_url`·`scope`는
서브도메인 루트(`/`)라 앱을 열면 곧바로 duri 홈이 뜬다(work 홈 경유 없음).

- **서비스워커(`sw.js`)는 푸시 알림 표시 + 앱 셸(문서·manifest·아이콘) 캐싱**
  둘 다 담당한다. `fetch` 핸들러가 stale-while-revalidate로 동작해 — 캐시가
  있으면 그걸 즉시 돌려주고, 최신본은 백그라운드에서 받아 다음 실행을 위해
  갱신해 둔다(카카오톡처럼 완전히 껐다 켜도 네트워크를 기다리지 않고 바로
  뜨게 하는 게 목적). `/_duri/`·`/_rt/`(실시간·게이트 API)는 항상 최신이어야
  하므로 절대 캐싱하지 않는다. 게이트 세션이 만료돼 `/`가 `/login`으로
  리다이렉트되는 경우, `fetch`가 그 리다이렉트를 자동으로 따라가 버려서
  캐싱하면 원래 URL 밑에 로그인 페이지가 깔릴 수 있어 `response.redirected`면
  캐싱을 건너뛴다. 서비스워커 등록 자체는 푸시 지원 여부와 무관하게 항상
  이뤄진다(`swReady`) — 예전엔 등록이 푸시 초기화 코드 안에 있어서 서버에
  VAPID 키가 없으면 캐싱까지 덩달아 꺼지는 문제가 있었다.
- 아이콘 PNG(iOS `apple-touch-icon` 고해상도용)는 지금 SVG 하나로 갈음한다.
- **스티커 팩 목록(`catalog.json`)도 로컬(`duri:packs`)에 캐싱**한다. 예전엔
  로그인 시 이 목록을 네트워크로 받아올 때까지 채팅 히스토리 렌더 자체가
  기다렸는데(`await loadPacks()`), 이미 기기 안에 있는 메시지를 그리는 일이
  스티커 팩이라는 무관한 네트워크 요청에 발목 잡히는 셈이라, 캐시로 즉시
  채우고 최신화는 백그라운드로 미뤘다.

## 움직이는 스티커 (v1 — 데이터 기반 모션)

파일(GIF/WebP)을 굽지 않는다. **투명 PNG 1장 + 키프레임 명세**를 Web Animations로
재생한다(`duri/index.html`의 `ANIM_PRESETS`·`STICKER_ANIM`·`playAnim`). 스티커
메시지는 여전히 `{sticker:{pack,n}}` 참조라 프로토콜·E2E·DO·싱크 변경은 없다.

- **명세**: 정규화 시간 키프레임. `{ at:0~1, translateX/Y(%), rotate(deg),
  scale|scaleX|scaleY, opacity }` + `duration`·`easing`·`iterations`·`origin`.
  프리셋(bounce·float·pulse·wobble·shake·jelly·tada·swing·heartbeat) 제공.
- **배정**: `STICKER_ANIM` 맵(팩 기본 / `"pack/n"` 개별 / `{cycle:[...]}` 장별
  순환). v1은 클라이언트에서 실험 — 값만 바꿔 재배포하면 즉시 반영. (데모로
  `couple-cat` 팩에 9종 모션을 순환 배정.) 나중에 팩 metadata/catalog로 옮긴다.
- **성능·접근성**: `IntersectionObserver`로 화면 밖이면 자동 일시정지,
  `prefers-reduced-motion`이면 정지(정적).

### 카카오/라인 내보내기 목표 (명세는 재작업 없이 재사용)

명세의 시간이 정규화(0~1)라 해상도·프레임수와 무관하다. 나중에 **같은 명세를
캔버스로 프레임 렌더 → GIF/APNG/WebP**로 구우면 두 스토어 규격을 맞출 수 있다.

- **작업 캔버스 720×720**(정사각), 최종은 다운스케일.
- **교집합 규격**: 정사각 **270~360** 안 구도, **12~20프레임**, **1~2초 루프**,
  배경 투명.
- 카카오: 360×360, ≤24프레임. 라인: 가로≤320·짧은변≥270, 5~20프레임, 재생 4초
  이내(정수 초 1/2/3/4, 재생시간×루프 ≤4초), 이미지당 ≤300KB.
- 즉, **Duri에서 반응 좋았던 모션 명세 = 그대로 내보내기 후보**. (렌더러는 추후
  구현. AI 캐릭터 정책은 스토어 제출 시점에 별도 확인.)

## E2E 암호화 (공유 패스프레이즈)

- 두 사람이 **같은 암호 문구**를 각자 최초 1회 입력 → PBKDF2(210k, SHA-256)로
  AES-GCM 256 키 파생. 문구·키는 기기를 떠나지 않는다.
- **문구 자체는 어디에도 저장하지 않는다.** 입력받은 즉시 키로 바꾸고 버린다.
  이 기기에 남는 것은 `extractable: false`로 유도한 **CryptoKey 객체**뿐이고,
  IndexedDB "meta" 스토어에 구조화 복제로 담긴다 — 담긴 뒤에도 원문 바이트를
  다시 꺼낼 수 없어서, 기기를 잠깐 빌려주거나 XSS가 나도 문구가 새지 않는다
  (예전에는 `localStorage["duri:pass"]`에 평문으로 있었다. 옛 기기는 페이지를
  한 번 열면 자동으로 키로 바뀌고 평문 문구는 지워진다).
- 남는 위험은 그대로 적어 둔다: 키 객체를 쥔 기기에서는 **그 기기에 한해**
  복호화가 계속 가능하고(=자동 입장의 대가), salt가 고정이라 문구가 짧으면
  암호블롭을 확보한 공격자의 오프라인 대입에 약하다. 문구는 길게 잡는다.
- 메시지·사진·발신자 이름·캡션까지 전부 암호화되어 오간다. 서버엔 `{ iv, ct }`
  불투명 값뿐. 문구가 다르면 상대 메시지는 "복호화 불가"로 표시된다.
- 문구 입력칸(`#pass`)은 `type="password"`가 아니라 `type="text"` +
  `-webkit-text-security: disc`로 화면엔 점만 보이게 가린다 — 일부 한국어
  키보드 앱이 실제 password 필드를 "보안 키보드"로 인식해 영문 전환 키
  자체를 빼버리는 문제가 있어서다.

## 채팅이 항상 맨 아래에서 시작하는 이유

스크롤 컨테이너(`#log`)를 **`flex-direction: column-reverse`** 로 두고, 메시지는
그 안의 `#log-inner`(`column`)에 정상 순서로 쌓는다. 이러면 **시각적 바닥이
`scrollTop === 0`** 이 되고, 콘텐츠가 늘어나도(사진이 늦게 디코딩되거나 주소창·
키보드가 정리돼 보이는 영역이 줄어도) 브라우저가 알아서 바닥을 유지한다. 메신저
UI의 표준 기법이다.

- **왜 직접 스크롤하지 않나**: 초기 렌더 직후 `scrollTop` 을 한 번 맞추는 방식은
  그 순간의 높이만 보고 끝난다. 그 뒤 사진이 붙으며 콘텐츠가 늘어나면 바닥이었던
  자리가 위로 밀린다 — 앱을 열면 채팅이 조금 올라간 자리에서 시작하던 게 이것이다.
- **왜 스크롤 앵커링에 기대지 않나**: `overflow-anchor` 는 **iOS Safari 가 전혀
  지원하지 않는다**(Chrome·Firefox만 지원). 데스크톱 Chrome 에서 이 증상이 재현되지
  않았던 것도 앵커링이 가려 줬기 때문이다. `column-reverse` 는 앵커링과 무관하게
  동작해서 아이폰에서도 같다.
- 좌표 규칙이 뒤집힌다: **0 이 바닥, 위로 갈수록 음수**. `scroll()`·`atBottom()`·
  `scrollToBottom()` 이 그 기준으로 되어 있다(`atBottom` 은 `scrollTop > -80`).
  스크롤 위치를 다루는 코드를 추가한다면 이 규칙을 따라야 한다.
- 스크롤 이벤트·탭 스와이프는 스크롤 컨테이너(`logBox()`)에서 받고, 메시지
  append·개수 정리는 안쪽(`log()`)에서 한다.

### 사진은 미리보기가 먼저 뜬다

사진은 원본(중앙값 2.5MB)을 압축 없이 그대로 보낸다 — 원본 보존이 이 앱의 원칙이라
화질은 손대지 않는다. 대신 **저해상도 미리보기(긴 변 320px, JPEG q0.6, 1~2KB)를
메시지 안에 그대로 실어** 보낸다. 텔레그램 `photoStrippedSize`·왓츠앱 envelope
thumbnail 과 같은 방식이다.

- **보내는 쪽**: 사진을 고른 순간 로컬 파일로 말풍선을 먼저 띄우고 업로드 진행률을
  채운다(`showPendingPhoto`, XHR `upload.onprogress` — fetch 로는 진행률을 알 수
  없다). 서버가 seq 를 발급해 broadcast 로 돌아오면 그 임시 말풍선을 걷어낸다.
  예전엔 업로드가 끝날 때까지 화면에 아무것도 없어 보낸 건지 알 수 없었다.
- **받는 쪽**: 미리보기가 실려 있으면 **원본을 기다리지 않고** 그걸로 즉시 그린다
  (2.5MB → 1~2KB). 원본은 뒤에서 동시 2장까지 최근 것부터 받아 `src` 를 갈아끼운다.
  메타의 `w`/`h` 로 `aspect-ratio` 를 미리 잡아 교체 순간에 화면이 튀지 않는다.
- **여기에 자물쇠가 하나 있다**: 원본을 아직 못 받은 사진이 있으면 `seen` 을 그
  앞까지만 보고한다(`awaitingPhoto`). 넘겨서 보고하면 서버가 그 사진을 지워 버려
  **미리보기만 남고 원본을 영영 못 받는다.**
- 미리보기를 못 만드는 형식(브라우저가 못 여는 HEIC 등)이나 16KB 를 넘는 경우엔
  아예 싣지 않는다 — 그 사진은 예전처럼 원본을 기다려 그린다.

### 접속 직후엔 최근 것만 받는다

예전엔 접속하면 서버 버퍼 전체(최대 1000개)를 한 번에 밀어 넣었다. 사진이 섞여
있으면 수십 MB 를 다 받아야 채팅이 떴다. 지금은 **최근 `BACKFILL_LIMIT`(100)개만**
보내고, `backfill-done` 에 `more`·`oldest` 를 실어 "그 앞이 더 있다"를 알린다.
위로 올려 캐시가 바닥나면 클라이언트가 `fetch-older` 로 그 앞 구간을 가져간다
(커서 기반 페이지네이션).

### 옛 대화 이어보기 (위로 올리면 계속)

앱을 열면 최근 `MAX_DOM`(300)개만 그린다. 예전엔 **그게 스크롤의 끝**이었고, 이
기기 캐시(IndexedDB, `MAX_CACHE` 2000개)에 멀쩡히 있는 그 앞 대화는 볼 방법이
아예 없었다 — 890여 건 중 600건쯤이 기기 안에 있으면서 화면에 못 뜨는 상태였다.

위로 올려 상단에 닿으면 캐시에서 `OLDER_BATCH`(100)개씩 이어 붙인다.

- 옛 묶음은 **따로 그린 뒤 통째로 앞에 삽입**한다(`appendRecord` 의 `into` 옵션).
  날짜 구분선·연속 발신자 그룹이 전역 상태라, 그 묶음 안에서만 다시 계산하려고
  잠시 비켜 두고 복원한다.
- `column-reverse` 라서 **위에 콘텐츠가 들어와도 보던 자리가 밀리지 않는다** —
  스크롤 위치를 손으로 보정할 필요가 없다.
- 위로 불러온 뒤에는 화면 상한을 `MAX_CACHE` 로 늘린다(`trimDom`) — 그대로 두면
  방금 불러온 옛 대화를 아래에서 자라는 정리 로직이 도로 잘라낸다.
- 캐시 맨 앞까지 가면 "여기가 이 기기에 남은 가장 오래된 대화예요" 안내가 뜬다.
  그보다 더 옛날은 **PC 백업(`DuriStorage/`)에만** 있고, 앱으로 되받아오는 기능은
  아직 없다(다음 단계 — 서버에 다시 올리는 일이라 경고와 명시적 버튼을 둘 예정).

## 화면 구성 (3-탭 좌우 스와이프)

화면은 **[채팅 | 캘린더 | 지도] 세 장**이고 좌우 스와이프로 넘긴다 — 왼쪽으로
밀면 다음 탭(오른쪽 화면 밖에서 끌려 들어온다), 오른쪽으로 밀면 이전 탭.
설정(⚙️) 메뉴의 📅·🗺️ 항목과 각 화면 헤더의 ‹ 버튼도 같은 일을 한다. 지도(2)를
열면 그 뒤에 캘린더(1)도 같이 열어 둬서, 지도를 오른쪽으로 밀면 캘린더가
나오는 순서가 자연스럽게 이어진다.

드래그 중엔 손끝을 그대로 따라가고(실시간 추적), 손을 뗀 순간 남은 진행률로
스냅한다 — 탭을 당겨오는 느낌. 열 때는 30%(`PANE_OPEN_AT`) 이상 끌어야 하지만,
돌아갈 때는 15%(`PANE_CLOSE_AT`)만 끌어도 닫힌다(뒤로가기는 가볍게).

## 공유 캘린더

채팅과 함께 쓰는 둘만의 캘린더(탭 1).

- **월간**: 날짜 아래에 최대 2개 제목을 작게 미리보기하고(넘치면 `+N`), 고른
  날의 일정은 격자 아래 패널에서 전체를 읽는다. 날짜를 **한 번** 누르면 선택만
  바뀌고 패널의 **＋ 일정**으로 추가하며, 같은 날짜를 400ms 안에 **두 번**
  누르면(더블클릭/더블탭) 그 날짜의 일정 추가 다이얼로그가 바로 열린다(네이티브
  dblclick 대신 클릭 타이밍으로 직접 판정 — 모바일 PWA 터치에서 더 안정적).
- **주간**: 하루 한 장의 카드 목록(어젠다). 카드를 누르면 그 날 일정 추가.
- **월간↔주간 전환**: 세그먼트 버튼(월/주) 외에, 격자 위에서 **아래로 스와이프하면
  주간, 위로 스와이프하면 월간**으로 바뀐다(구글 캘린더 제스처 벤치마킹). 좌우
  스와이프(채팅↔캘린더)와 방향 우세로 서로 간섭하지 않는다.
- **월 이동**: 세로 스와이프가 월/주 전환에 이미 쓰이므로, 월간 화면 맨 아래에
  **‹ 저번달 / 다음달 ›** 버튼을 따로 둔다(엄지로 누르기 쉬운 위치). 헤더의
  ◀ ▶ 도 같은 동작.
- 일정은 **종일**이거나 **시작·끝 시간**을 갖는다. 정렬은 종일 먼저, 그다음 시작시간.
- 분류는 `내 일정`·`공통` 둘뿐이다. 개인 일정(`owner` 필드 = 만든 사람 이름)의
  색은 **이름에 묶인다** — 기기별로 "내 색/상대 색"을 따로 고르던 예전 방식은
  **어느 쪽에서 보느냐에 따라 같은 일정이 다른 색으로 보이는 버그**가 있어서
  (내 기기의 mine/theirs가 상대 기기에선 반대로 뒤집힘) 없앴다. 아직 아무도
  안 골랐으면 이름 문자열을 해시해 고정 팔레트(`OWNER_PALETTE`, 8색)에서 기본값을
  고르고(`colorForOwner`), 🎨에서 **이름별로 직접 고를 수도 있다** — 그 경우
  고른 값이 markers와 같은 `cal:<id>` LWW 저장소로 동기화돼(`palettecolors`
  고정 id, `kind:"palette"`, `{byName, shared}`) 어느 쪽에서 바꾸든 양쪽
  기기가 같은 색을 본다 — **공통(`shared`) 일정 색도 같은 레코드로 동기화**된다
  (예전엔 기기별 로컬 설정이라 둘이 다르게 고르면 서로 다르게 보였다).
  상대 이름은 물어보지 않고 상대가 만든 일정·메시지가 한 번이라도 오면 그때
  로컬(`duri:peername`)에 기억해 뒀다가 색상 설정에 자동으로 칸을 띄운다.
- "오늘" 버튼은 오늘이 화면 밖에 있을 때만 나타난다.
- **일정 색**: 종일 일정은 색을 꽉 채운 알약 + 흰 글자, 시간 일정은 배경 없이
  색점 + 지금까지와 같은 글자색(배경과 비슷하게 옅다). 글자는 굵게(800) + 자간을
  좁혀 좁은 칩 안에 최대한 많은 글자가 보이게 했다. 팔레트도 파스텔톤(더스티
  로즈·블루·올리브·브라운·퍼플·틸 등)으로 낮췄다 — 다만 흰 글자가 읽혀야 해서
  아주 옅은 파스텔까지는 못 가고 채도만 낮춘 중간 톤이다(대비비 4:1 안팎으로
  확인).
- **월간 뷰의 일정은 하루짜리든 여러 날이든 같은 위계(같은 줄)에 함께 놓인다**
  (구글 캘린더 벤치마킹) — 하루짜리는 자기 칸 하나만큼, 여러 날 일정은 그만큼
  넓게 막대를 차지하며 같은 레인 배치 규칙을 공유한다. 겹치는 게 있으면 자동으로
  다음 레인에 쌓고(2인용이라 자주 겹치진 않아 단순한 그리디 배치로 충분), 레인이
  3줄을 넘으면 그 아래는 요일별 "+N"으로 접는다. 여러 날 일정은 같은 주
  안에서는 제목이 한 번만 보이고 주가 바뀌면 그 주에서 다시 한 번(반복 일정은
  회차마다 그 날짜에 하루짜리로 따로 그려서 "이 날짜만 삭제"가 회차를 구분할
  수 있게 한다). 막대가 날짜 숫자보다 위로 올라오지 않도록, 한 주는 [날짜 숫자
  줄 → 일정 막대 레인 → 빈 탭 영역] 순서로 그린다(`.cal-week-dates` →
  `.cal-week-bars` → `.cal-week-days`).
- **표식(스티커/이모지)**: **일정이 아니라 날짜 자체**에 붙는다 — 글로 남기기
  애매한 걸 이모지 하나로 표시할 때 쓴다. day 패널 헤더의 별(⭐) 버튼을
  누르면 8칸 팝업이 근처에 뜬다 — 첫 칸은 항상 "✕ 지우기", 나머지 7칸은
  미리 골라 둔 이모지(`MARKER_EMOJIS`)라 그중 하나를 누르면 그 날짜에
  담긴다(직접 타이핑하지 않음). 일정과 분리돼 있어서 일정을 하나도 안
  만들어도 표식만 남길 수 있고, 월간 뷰의 일정 막대(레인)를 전혀 차지하지
  않는다 — 항상 날짜 숫자 옆 배지(.8rem 이모지)로만 보여서 다른 일정들과
  자리다툼이 없다. 구현은 같은 `cal:<id>` 저장소를 재사용하되 id를 날짜에서
  결정적으로 만들어(`mk20260810` 식) 날짜당 하나만 존재하게 하고
  `kind:"marker"` 로 표시해 일반 일정 목록·반복 계산에서 제외한다
  (같은 LWW·방초기화·오프라인 큐를 그대로 물려받는다).
- **한국 공휴일**은 🇰🇷 표시로 자동으로 뜬다(서버에 저장하지 않는 가상 이벤트라
  양쪽 기기가 각자 계산 — 공개 정보라 굳이 암호화·동기화할 필요가 없다). 색은
  내꺼/상대꺼/공유와 겹치지 않는 별도의 빨강(`calColors.holiday`, 요일 헤더의
  일요일 빨강 `--sun`과 같은 톤)이라 실제 공유 일정과 한눈에 구분된다. 신정·삼일절·노동절·어린이날·현충일·제헌절·광복절·개천절·한글날·
  크리스마스 같은 **고정일은 연도 상관없이 대체공휴일까지 계산**해서 나오지만,
  **설날·추석·부처님오신날(음력)은 변환 로직이 없어 확인해 둔 2026·2027년치만**
  들어 있다(그 뒤 연도가 필요해지면 `LUNAR_HOLIDAYS`에 추가). 설날·추석은 여러
  날 공휴일이라 위 막대 표시를 그대로 탄다. 탭하면 수정 다이얼로그 대신 이름만
  토스트로 뜬다 — 실제 일정이 아니라 고치거나 지울 수 없다.
- 일정 추가 다이얼로그는 제목 입력창에 포커스가 가면 키보드가 뜨는데, 이때
  `visualViewport` 로 실측한 키보드 높이(`--kb-live`)만큼 하단 여백을 늘려
  **키보드 위 보이는 영역 안에서** 가운데 정렬한다(전체 화면 기준으로 정렬하면
  키보드에 가려질 수 있어서). 카드가 그 영역보다 크면 카드 안에서 스크롤.
- **다이얼로그** (네이티브 캘린더 앱 벤치마킹): 제목은 테두리 없는 큰 글씨
  입력(placeholder "제목"). 시작일·종료일은 화살표(→/←) + 전체 날짜 텍스트
  행으로 보여주고, 행 전체가 탭 영역이라 어디를 눌러도 네이티브 날짜 피커가
  뜬다(둘 다 직접 편집 가능 — 시작일을 나중 날짜로 옮기면 종료일도 못 미치지
  않게 따라온다). "종일"은 iOS식 on/off 토글이고, 켜져 있으면 시작·끝 시간
  입력은 아예 감춘다. "반복"은 기본 접힌 칩(🔁 반복)이라 눌러야 주기·종료
  옵션이 펼쳐진다 — 대부분 일정은 반복이 아니라서 폼을 가볍게 유지한다.
- **여러 날에 걸친 일정**: 종일 + 종료일을 시작일보다 뒤로 잡으면 그 범위의 모든
  날짜에 나타난다(각 날짜에 같은 제목이 반복 표시되는 방식 — 격자 칸을
  가로지르는 띠는 아니다).
- **반복 일정**: 반복 토글을 켜면 **주기**(매일/매주/매월/매년) + **종료**
  방식(계속/날짜까지/횟수만큼, 예: "5번")을 고른다. 회차마다 따로 저장하지
  않고 **시리즈 하나(시작일 + 규칙)로 계산**해서 매번 그려진다. 매월 반복은
  시작일이 31일이면 31일이 없는 달은 자연히 건너뛴다(예: 1/31 매월 → 2월엔
  없고 3/31에 다시). **여러 날 종료일과 반복은 함께 쓸 수 없다**(반복 설정 시
  종료일 무시, 다이얼로그에 안내 문구).
- **반복 일정 삭제**: **이 날짜만 삭제**(그 회차만 `recur.exclude` 목록에 넣어
  건너뛰고 나머지 시리즈는 유지) / **전체 삭제**(시리즈 전체를 지운다) 둘 중
  선택한다. 제목·시간 등 다른 값을 고쳐 저장하는 일반 편집은 여전히 시리즈
  전체에 적용된다 — "이 회차만 제목 바꾸기" 같은 예외 편집은 없다.

### 일정 댓글

일정 수정 다이얼로그 아래에서 그 일정에 **댓글**을 달 수 있다. 작성자 이름과
시각이 함께 남고, **자기 댓글만** 지울 수 있다(실수로 상대 말을 지우는 쪽이 더
곤란해서). 달린 일정은 월간·주간 칩에 `💬N` 배지가 붙어 열어보기 전에도 알 수 있다.

- **저장은 일정 안이 아니라 별도 `cal:<id>` 레코드**(`kind:"comment"`,
  `{eventId, text, author, at}`)다. 일정 content 안에 배열로 넣으면 LWW 때문에
  한쪽이 댓글을 다는 사이 다른 쪽이 제목을 고치면 rev 큰 쪽만 남아 **댓글이 통째로
  사라진다**. 레코드를 나누면 각자 독립적으로 합쳐지고, 표식·색설정과 같은
  저장소라 동기화·오프라인 큐·방초기화·PC백업을 그대로 물려받는다.
- **새 일정에는 댓글칸이 없다** — 저장하지 않고 취소하면 고아 댓글만 남는다.
  저장한 뒤 다시 열면 보인다.
- **일정을 지우면 그 댓글도 함께 지운다**(고아 방지).
- PC 백업의 `calendar.md` 에는 일정 바로 아래에 `- 💬 이름: 내용` 으로 붙는다.

### 저장·동기화 (채팅 버퍼와 다르다)

채팅·사진은 싱크가 ack 하면 서버에서 사라지는 **버퍼**지만, 캘린더는 계속 남아야
하므로 DO 스토리지의 **지속 상태**로 둔다. **데스크톱 싱크도 캘린더를 백업한다**
(`DuriStorage/calendar/`) — 접속 때 `cal-hello` 로 전체를 받고 이후 변경을
따라가되, 서버에 없는 항목은 지우지 않고 병합한다(방초기화로 서버가 비워져도
PC 사본은 남는다). 이벤트 하나가 키 하나(`cal:<id>`)이고
값은 E2E 암호블롭 `{iv, ct}` + `rev`(수정시각). 양쪽이 같은 일정을 고치면 **rev
큰 쪽이 이긴다**(last-write-wins). 삭제는 툼스톤(`deleted:true`)으로 전파된다.
접속하면 `cal-hello` → `cal-state`로 전체를 받고, 이후 변경은 `cal-put`/`cal-del`로
중계된다. 오프라인 중의 변경은 클라이언트 `calOutbox`에 쌓여 재접속 때 보낸다.
이 기기 사본은 `localStorage["duri:cal"]`(새로고침 시 즉시 그리기용).

### 아직 안 된 것 (알고 쓰는 한계)

- **툼스톤이 정리되지 않는다.** 삭제 표시가 영구히 남고 `MAX_CAL_EVENTS`(2000)
  카운트에 포함된다 → 만들고 지우기를 2000번 반복하면 새 일정이 조용히 거부된다.
- 반복 일정은 **회차별 예외가 없다**(하나 고치면/지우면 시리즈 전체). 알림은 없다.

### 채팅에서 "/일정" 명령으로 추가

채팅 입력창에 `/일정 제목`을 타이핑하면 입력창 위에 **📅 일정 칩**이 뜬다(그대로
Enter를 쳐도 칩을 누른 것과 같다). 누르면 이번달+다음달을 보여주는 미니 달력이
열리고, **아고다식으로 시작일을 한 번, 종료일을 한 번 더 탭**하면(같은 날을
두 번 탭하면 하루짜리) 그 자리에서 바로 종일 일정이 추가된다. **시간 지정·반복은
지원하지 않는다** — 텍스트로 "이 반복 일정 지워줘" 같은 걸 안전하게 특정하기
어렵고 잘못 지우면 공유 캘린더라 되돌리기도 번거로워서, 명령은 의도적으로
추가 전용+ 종일/여러 날만 지원한다. 시간·반복이 필요하면 캘린더 탭에서 편집.

성공하면 상대도 볼 수 있게 채팅에 **오픈카톡 입장 메시지 같은 시스템 알림**
("📅 "test" 일정 추가됨 (7/26 (일))")을 하나 남긴다 — 일반 말풍선과 안 헷갈리게
가운데 정렬 알약으로 그린다. 이 알림도 다른 메시지와 똑같이 **진짜로 E2E
암호화되어 상대·PC 백업에 남는다**(`sys` 플래그로 렌더링만 다르게 할 뿐, 프로토콜
상으로는 평범한 `msg` 항목). 새 일정은 기본 **공통**(양쪽 다 보임)으로 만들어진다
— 색·소유자를 바꾸려면 캘린더 탭에서 편집.

## 사진 (촬영 위치 · 정보 · 삭제)

- **촬영 위치(EXIF GPS)를 보내기 전에 뽑아 E2E 메타에 담는다** — 의존성 없는
  최소 JPEG 파서(`exifGps`)라 HEIC/PNG처럼 못 읽는 형식은 그냥 `null`이다.
  서버는 원본 바이트도 메타도 암호블롭으로만 보므로 위치를 알지 못한다. 이
  값이 아래 "함께 다닌 곳 지도"의 재료다. **안드로이드는 갤러리에서 고를 때
  EXIF가 대개 비어 있다** — 그래서 위치를 넣는 다른 두 길(📍 현재 위치 추가,
  지도에서 지역 콕 찍어 추가)을 따로 뒀다.
- **트레이 사진을 누르면 정보 시트**가 뜬다(파일명·해상도·기기·촬영시각·위치).
  위치가 있으면 "지도에 표시돼요"라고 알려줘서, 보내기 전에 지도에 담기는지
  바로 확인할 수 있다.
- **꾹 누르면 삭제 버튼**이 뜨고, 누르면 `{type:"del", seq}`를 보낸다. 서버가
  버퍼 항목과 **R2 원본까지 지우고** `deleted`를 브로드캐스트해 **양쪽 기기**의
  화면·IndexedDB 캐시·지도 핀에서 함께 사라진다(`DuriDO.deleteEntry`).
  브라우저만 지울 수 있다(싱크 토큰으로는 불가). **이미 싱크가 받아 간 PC
  아카이브 원본은 그대로 남는다** — 엣지에서만 지워지는 것이다.

## 함께 다닌 곳 지도

둘이 다녀온 **시군구를 색칠하는 한국 지도**(탭 2). 설정(⚙️) 메뉴의
🗺️ 항목으로 열고, 채팅↔캘린더와 같은 좌우 스와이프로도 오간다.

- **외부 타일·지도 API를 쓰지 않는다**(estate와 같은 방식). 리포에 커밋된
  시군구 경계 `duri/data/kr-sgg.geojson`(WGS84, 약 390KB)을 받아 SVG path로
  직접 그리고, 핀은 점-폴리곤 판정(`pointInPolys`, ray casting)으로 시군구에
  배정한다. 투영은 위도 보정만 넣은 등거리 투영이고 한국 bbox를 viewBox에 맞춘다.
- **핀은 캘린더와 같은 `cal:<id>` 저장소로 동기화된다**(`kind:"pin"`, id 는
  `pin<seq>` 로 결정적이라 seq 당 하나). 예전엔 기기 로컬(`localStorage`)에만
  쌓고 서버로 보내지 않았다 — 양쪽이 같은 메시지를 받아 각자 같은 지도를 만든다는
  전제였는데, **PC 백업(싱크)을 켜면서 그 전제가 깨졌다**: 싱크가 ack 하면 서버가
  항목을 바로 버리므로, 그 순간 접속해 있지 않던 기기는 그 핀을 영영 만들지
  못한다(두 사람 지도가 갈라진 원인). 지금은 핀 자체가 공유 상태라 동기화·LWW·
  오프라인 큐·방초기화·PC백업을 캘린더에서 그대로 물려받는다.
  - **`owner` 에는 이름을 담는다**(`mine` 같은 기기 기준 값이 아니라) — 저장된
    값이 기기마다 다르게 해석되면 같은 핀이 양쪽에서 다른 색으로 보인다.
    캘린더 일정 색에서 이미 겪은 버그라 같은 실수를 반복하지 않는다.
  - 사진·메시지가 삭제되면 그 핀도 툼스톤으로 함께 지워진다.
  - 옛 로컬 핀(`duri:pins`)은 지도를 처음 열 때 한 번 공유 저장소로 옮기고
    비운다(`migrateLocalPins`). 지웠던 핀은 툼스톤으로 올려 되살아나지 않게 한다.
- **🔄 수동 동기화**(지도 헤더). 이 기기 캐시(IndexedDB)를 다시 훑어 빠진 핀을
  만들고 `cal-hello` 로 상대 핀도 끌어온다. 자동으로도 맞춰지지만, 옛 기록에서
  핀을 새로 만들어야 하거나 한쪽이 오래 꺼져 있었을 때 눌러 맞춘다.
- **위치를 담는 세 가지 길**: ① 사진 EXIF GPS(`loc`) ② 채팅에 **`/여기`**(또는
  `/here`)를 치면 브라우저 Geolocation으로 현재 위치를 E2E 메시지(`here`)로
  보낸다 — 문자로는 안 가고 채팅엔 가운데 알약으로 표시된다. 지도 헤더의
  **📍 현재 위치 추가** 버튼도 같은 동작 ③ 지도에서 지역을 탭해 그 지역
  앨범에 사진을 추가(아래).
- **현재 위치는 사람이 확정한다.** 첫 GPS fix는 기지국·와이파이 기반이라 수백
  m~수 km씩 틀려서 옆 구에 찍히곤 했다. 그래서 ⓐ `watchPosition`으로 최대 9초
  동안 정확도가 좋아지는 fix를 고르고(±40m면 즉시 채택, `maximumAge:0` — 예전엔
  30초 전 캐시 fix를 그대로 썼다) ⓑ **확인 시트**에 판정된 시군구와 오차를
  보여준다. 오차 반경(±1.5배, 최소 200m)에 다른 시군구가 걸리면 **후보 칩**으로
  함께 띄워 고르게 한다 — 정확도를 아무리 높여도 경계 바로 옆이면 기계는 틀릴
  수밖에 없어서, 마지막 판단은 사람이 한다. 후보를 고르면 그 지역 **대표점**
  좌표로 보내 확실히 그 구에 찍히고, 그대로 확인하면 실제 GPS 좌표를 쓴다.
- **잘못 찍힌 색칠은 지운다.** 지역 앨범의 **🧹 이 지역 색칠 지우기** — 그 지역
  핀만 빼고 **사진·대화는 그대로 남긴다**. 핀은 메시지에서 파생되므로 목록에서
  빼기만 하면 다음 히스토리 재생 때 되살아난다 → 지웠다는 사실을 툼스톤
  (`duri:pinsHidden`)으로 남기고, **`unpin` 메시지로 상대 기기에도 전파**한다
  (채팅에는 안 그려지는 조용한 제어 항목이지만 프로토콜상 평범한 `msg`라 E2E는
  그대로). 끊겨 있으면 `duri:unpinOutbox`에 쌓아 재접속 때 보낸다.
- **원은 지역별 클러스터다**(부동산 앱 벤치마킹). 예전엔 위치가 있는 항목마다
  같은 크기의 점을 하나씩 찍어서, 많이 간 곳일수록 점이 겹쳐 뭉개지고 작은
  구에서는 점 하나가 구보다 커 보였다. 지금은 지역별로 묶어 **개수에 따라 크기가
  다른 원 하나**를 찍는다(1~4·5~19·20~49·50~99·100+ 다섯 단계, 화면에서 충분히
  크면 개수도 숫자로).
  - **배율 3배를 넘으면 시도 → 시군구로 쪼갠다**(`SGG_ZOOM`). 멀리서는 "서울 32",
    당기면 "강남구 30"이 된다.
  - **원 지름은 그 구역 짧은 변의 50%를 넘지 않는다** — 원이 구역을 덮으면 어디를
    탭해야 할지 알 수 없다. 동시에 반지름을 배율로 나눠 **화면에서 보이는 크기를
    일정하게** 유지한다(SVG가 통째로 확대되므로 그냥 두면 같이 커진다). 하한도
    배율로 나눈다 — 고정값으로 두면 확대할수록 모든 원이 하한에 걸려 개수에 따른
    크기 차이가 통째로 사라진다.
  - 원은 **실제로 찍힌 좌표들의 평균**에 놓는다. 구역 bbox 중심을 쓰면 인천처럼
    먼 섬을 가진 시도의 원이 서해 한복판에 뜬다.
  - 배율이 바뀔 때만 다시 그리고(팬만 하면 그대로), 핀치 중에는 프레임당 한 번으로
    합친다(`scheduleDots`).
- **색은 올린 사람 기준**: 그 시군구에 나만 올렸으면 내 색, 상대만이면 상대 색,
  둘 다면 공통 색. **캘린더 팔레트(`colorForOwner`/`sharedColor`)를 그대로
  재사용**해서 양쪽 기기가 같은 색을 본다. 사진이 많은 곳일수록 진하다
  (불투명도 0.4~0.95). 범례·요약은 각자 설정한 실제 이름으로 뜨고
  요약은 아이콘 + 숫자로 짧게 적는다 — `🧭 2  📷 1  📍 3`(시군구·사진·위치),
  해외가 있으면 `🌏 N`. **사진과 `/여기` 위치를 나눠 센다** — 예전엔 핀 개수를
  전부 "사진 N장"으로 적어, 위치만 남긴 것까지 사진으로 잡혀 숫자가 부풀었다.
  종류를 모르는 옛 핀(플래그가 없던 시절 것)이 섞여 있으면 나누지 않고 `📌 N`
  하나로 통칭한다. 지도를 열 때 이 기기 캐시에서 종류를 한 번 보정한다
  (`migratePinKinds`). 이모지만으로는 뜻이 안 통하니 `title` 로 이름을 붙여 둔다.
- **지역 앨범**: 시군구를 탭하면 그 지역 사진만 모아 보여주는 시트가 열리고
  (IndexedDB 캐시에서 위치로 필터), **＋로 이 지역에 사진을 추가**할 수 있다.
  이때 위치는 그 지역 안이 보장되는 대표 좌표(`regionPoint`)로 직접 붙이므로
  **EXIF가 지워진 안드로이드 사진도 지도에 담긴다**. 사진 점(`circle`)은
  `pointer-events:none` — 클릭을 먹으면 점 위를 탭했을 때 밑의 시군구가 안 잡혀
  **사진이 많은 지역일수록 앨범이 안 열렸다**(2026-08-11 수정). 색칠은 됐는데
  앨범이 비어 있으면 위치만 남긴 곳이거나 사진이 캐시에서 정리된 경우라, 시트가
  그렇게 설명한다.
- **핀치 확대(최대 16배) + 팬**: `#map-wrap`의 `touch-action:none`으로 브라우저
  기본 줌을 끄고 CSS transform으로 지도만 확대한다(페이지는 안 움직임). 작은
  구를 정확히 탭·사진추가하기 위한 배율이다. **팬과 탭 스와이프는 하나의 제스처
  판정으로 통합**했다 — 확대 상태(>1배)의 한 손가락은 지도 내 이동, 기본 배율의
  오른쪽 스와이프는 캘린더로 넘기기, 그 외(왼쪽·세로)는 무시. 확대·이동 직후의
  `click`은 지역 선택으로 치지 않는다(`mapMoved`). 지도를 열 때는 항상 배율 1로
  초기화한다.

### 아직 안 된 것 (알고 쓰는 한계)

- **핀이 캘린더와 저장소·상한을 공유한다.** 서버는 E2E라 `kind` 를 볼 수 없어
  일정과 핀을 구분하지 못하므로, `MAX_CAL_EVENTS`(2000)는 **둘을 합쳐** 센다.
  위치가 담긴 기록이 수천 건이 되면 일정 추가가 거부될 수 있다(그때는 `cal-reject`
  로 알린다).
- **지역 앨범은 IndexedDB에 남아 있는 사진만 보여준다.** 핀은 동기화되므로 지도
  색칠은 양쪽이 같지만, 그 지역 사진을 열었을 때 보이는 것은 기기마다 다르다 —
  싱크가 ack 해서 서버에서 폐기된 뒤 캐시에서도 밀려난 사진은 그 기기에 없다.
- 시군구 경계는 한국뿐이라 해외는 색칠되지 않고 요약에 장수만 센다.

## 새 메시지 푸시 알림 (기본 꺼짐)

설정(⚙️) 메뉴의 **🔔 푸시 알림** 토글로 기기별로 켠다(기본 꺼짐). 켜면 상대가
메시지·사진·스티커를 보낼 때 이 기기로 브라우저 알림이 온다(카톡 벤치마킹).
소리·진동은 따로 켜고 끌 수 없다 — 웹 푸시 API엔 커스텀 사운드가 아예 없고
진동 패턴도 iOS Safari는 지원하지 않아, 켜고 끄는 옵션 자체가 플랫폼마다
다르게 동작해 혼란만 커질 것 같아 뺐다(OS 기본 동작을 그대로 따른다).

- **서버는 알림을 보낼 때도 평문을 모른다.** 푸시 페이로드엔 채팅과 똑같은
  암호블롭(`{iv,ct}` 또는 사진의 `{metaIv,metaCt}`)만 실어 보내고, **`duri/sw.js`가
  이 기기 안에서 그 자리에 복호화**해서 보낸 사람 이름과 내용을 알림에 채운다.
  텍스트는 그대로, 사진은 "사진", 스티커는 "(이모티콘)"으로 뜬다(캡션·스티커
  이미지 자체는 안 보여줌). 브라우저 푸시 중계 서버(FCM 등)는 암호문만 스쳐
  간다 — 평문이 서버·중계 어디에도 남지 않는다.
- **복호화 키는 IndexedDB "meta" 스토어**의 CryptoKey 객체다(로그인 시 저장).
  `localStorage`는 서비스워커에서 못 읽어서 여기에 두고, 페이지도 같은 것을 읽어
  자동 입장한다 — 문구 문자열은 페이지·서비스워커 어디에도 없다. 문구를 다시
  입력하면 이 키도 함께 지워진다.
- **내가 보낸 메시지는 내 기기에 알리지 않는다.** 서버는 발신자를 구분하지 못해
  구독된 모든 기기에 그대로 브로드캐스트하므로, 복호화한 뒤 메시지에 실린
  `name`을 같은 "meta" 스토어에 저장된 내 이름과 비교해 일치하면 알림을 띄우지
  않는다(`duri/sw.js`의 `buildNotification`). 둘이 같은 이름을 쓰면 서로 구분이
  안 돼 이 필터가 무의미해진다 — 채팅 말풍선 좌우 정렬도 같은 이름 비교를 쓰므로
  기존 제약과 동일하다.
- 페이로드가 너무 크면(긴 텍스트 등, 3KB 초과) 내용 없이 "새 메시지가 도착했어요"
  일반 알림으로 대체된다(`DuriDO.buildPushPayload`).
- **이 기기에서 앱 화면을 이미 보고 있으면(포커스 중) 알림을 띄우지 않는다** —
  `sw.js`가 `clients.matchAll()`로 **포커스된** 창이 있는지 확인하고, 있으면
  조용히 넘어간다(웹소켓으로 화면에 이미 뜨는데 알림까지 겹칠 필요가 없다).
  백그라운드에 있거나 앱을 안 열어 둔 기기에만 뜬다.

### iOS(아이폰)에서 알림이 조용히 죽는 이유

iOS 웹푸시는 **홈 화면에 추가한 PWA에서만** 되고(Safari 탭에서는 아예 불가),
`pushsubscriptionchange`를 지원하지 않아 구독이 회전하면 **앱을 다시 여는 것
말고는 복구할 길이 없다**. 더 고약한 건 **silent push 예산**이다 — 푸시를 받고도
알림을 띄우지 않으면 iOS가 그걸 세다가 결국 **구독 자체를 취소**해 버린다.

- 그래서 포커스 판정을 `focused === true` **하나만** 믿는다(2026-08-11 수정).
  예전엔 `visibilityState === "visible"`도 함께 봤는데, iOS는 백그라운드로
  내려간 PWA 창을 "visible"로 보고하는 경우가 있어 **알림을 건너뛰고 → silent
  push로 세이고 → 구독이 취소되는** 경로가 열려 있었다.
- 남은 silent push 경로 하나: **내가 보낸 메시지가 내 다른 기기로 갈 때**.
  서버는 E2E라 발신자를 몰라 구독된 모든 기기에 보내고, 접속 중인 기기만
  건너뛴다 — 그래서 내가 PC에서 보내면 백그라운드의 내 폰에 푸시가 가고,
  `sw.js`가 이름을 보고 알림을 억제한다(=silent). 한 사람이 기기를 여러 대
  쓸 때만 생기고, 서버가 발신자를 알 방법이 없어 지금은 감수한다.
- 아이폰에서 알림이 안 오면 순서대로 확인: ① 홈 화면 앱으로 열었는지(사파리
  탭이면 불가) ② 설정 ⚙️ → 🔔 테스트 알림 결과 ③ iOS 설정의 알림 허용.
- 구독은 `sink`(데스크톱 데몬)가 아니라 **브라우저(peer)만** 가능하고, 최대
  8개까지(두 사람 × 기기 몇 대). 방 초기화는 구독을 건드리지 않는다.
- **구독 회전 때문에 알림이 조용히 끊기던 문제**(2026-08-11 수정). 브라우저는
  배포·SW 갱신 때 push endpoint를 바꾸는데, `pushsubscriptionchange`는 잘
  발생하지 않고(iOS는 미지원) 앱 시작 시의 재등록은 **새 구독을 추가만** 하고
  옛 것을 지우지 못했다 → 죽은 구독이 8칸을 채우면 그때부터 **새 구독이 503으로
  거절**되어 그 기기는 영영 알림을 못 받았다(클라이언트도 실패를 삼켜서 화면엔
  "켜짐"으로 보였다). 지금은 ⓐ 클라이언트가 기기 고유 **`deviceId`**
  (`duri:deviceId`)를 함께 보내 서버가 **같은 기기의 옛 구독을 지우고**
  ⓑ 슬롯이 차면 거절 대신 **가장 오래된 구독을 밀어내며**(구독마다 `at` 기록)
  ⓒ 재등록이 거절되면 **토스트로 알린다**.
- VAPID 키는 새로 만들지 않고 리포에 **이미 있는 걸 재사용**한다(`util/fortune`·
  `podcast`와 공유, `wrangler.jsonc`의 `VAPID_PUBLIC_KEY` + `VAPID_PRIVATE_KEY` secret).

## 서버 구성 (bubblelab 리포 안에서 자립)

- `_infra/duri.js` — `DuriDO`: 릴레이 + 버퍼(`buf:<seq>`, ack 시 폐기) + 사진
  R2 임시 보관 + 공유 캘린더 지속 상태(`cal:<id>`, LWW) + 웹 푸시 구독
  (`push:<hash>`, `_infra/webpush.js` 재사용, VAPID는 fortune·podcast와 공유).
  WS 메시지: `hello`/`msg`/`ack`/`del`/`cal-hello`/`cal-put`/`cal-del`/
  `presence-endpoint`. 상한은 파일 맨 위 상수에 모아 뒀다(사진 96MB, 버퍼 5000개,
  미ack 30일, 접속 8개, 캘린더 2000개, 푸시 구독 8개).
- `_infra/worker.js` — `handleDuriGate`(서브도메인 게이트), `/_duri`(WS 중계),
  `/_duri/photo`(업로드/다운로드), `/_duri/push`(GET 공개키 · POST/DELETE 구독,
  peer 전용), `/_duri/sink-token`(소유자 발급), `/_duri/reset`(소유자 방 초기화).
  인증: duri 게이트 세션(`bl_duri`, 브라우저) 또는 싱크 토큰(데몬). 비밀번호는
  `DURI_PASSWORD`(없으면 `WORK_PASSWORD` 폴백).
- `duri/sw.js` — 서비스워커: **푸시 알림 표시 + 앱 셸 캐싱**(위 "앱화" 참고).
  페이로드 복호화는 이 파일 안에서 직접(`index.html`의 `deriveKey`/`decryptJson`과
  로직 동일해야 함). 앱 셸을 고쳤으면 `SHELL_CACHE` 버전(`duri-shell-vN`)을 올린다.
- `duri/data/kr-sgg.geojson` — 지도용 시군구 경계(커밋된 정적 데이터, 외부 API 없음).
- `wrangler.jsonc` — `DURI` DO 바인딩·마이그v10, `DURI_BUCKET`(R2), `ENABLE_DURI` var.

## 켜는 법 (fail-closed)

`ENABLE_DURI`는 기본 `false`. 켜기 전에:

```bash
npx wrangler@4 r2 bucket create bubblelab-duri
npx wrangler@4 secret put DURI_PASSWORD      # duri 전용 게이트 비번(권장). 없으면 WORK_PASSWORD 폴백
npx wrangler@4 secret put DURI_SINK_SECRET   # 선택: 싱크 토큰 전용 서명키(비번 갈아도 토큰 유지)
# wrangler.jsonc 의 ENABLE_DURI 를 "true" 로 바꾼 뒤 배포
```

버킷·비밀번호(`DURI_PASSWORD`|`WORK_PASSWORD`)가 없으면 `/_duri`는 503으로 닫힌다.
비번을 갈면서도 데스크톱 싱크를 안 끊으려면 `DURI_SINK_SECRET`을 미리 걸어 둔다.
