# puzzle 난이도 측정기 — 기획

상태: **Phase 1 + 자동 재배치 + 유사도 검출 구현됨**. 9종 전체가
(picklock은 스코어제로 개편되어 slop으로 승격 — 집계 제외)
`window.blDiffAt(stage)`로 0~100 점수를 노출하고 HUD에 ★~★★★★★를
표시한다. 생성형 게임의 `genTuned()`는 후보 판(salt 시드)을 몇 개 만들어
`(목표 곡선 targetD(s) = min(90, 5 + 4.7s) 와의 거리) + 30 × (직전 두
스테이지 구조 지문과의 자카드 유사도)` 점수가 최소인 판을 채택한다 —
난이도 재배치와 "또 같은 판" 방지를 동시에. 구조 지문(`fpOf`)은 게임별
토큰 집합(관 구성, 차량 배치, 조각 분할, 문 순서, 모듈 열…)이고, 이웃
지문은 살트0 구조(`structFp`)라 스테이지의 순수 함수 — 시드 고정 결정론
(모두 같은 판)이 유지된다. 검증값은 `window.blSimAt(stage)`(인접 채택판
유사도)로 노출. picklock도 노치 배열 후보 중 최저 유사도를 고른다.
Phase 2(실측 텔레메트리)·3(대시보드)은 아래 기획대로 남아 있음.
실측이 쌓이면 targetD와 게임별 가중치를 보정한다.

생성된 레벨의 난이도를 숫자로 만들어
① 스테이지 커브를 의도대로 제어하고 ② 플레이어에게 별점으로 보여주고
③ 실제 데이터로 측정기가 맞는지 검증하는 것이 목표.

## 왜 필요한가

지금 제너레이터들은 난이도를 간접 지표로만 제어한다(트래픽 잼: 최단 이동
수 밴드, 주차: 교차 쌍 수, 얼음: 여유 곡괭이 수…). 이 지표들이 실제
체감 난이도와 얼마나 일치하는지 모르고, 게임끼리 단위도 제각각이다.
공통 척도(0~100)가 생기면 "스테이지 n은 난이도 d±ε 판만 채택" 방식으로
모든 게임의 커브를 같은 언어로 조율할 수 있다.

## 구조: 2층 측정

### 1층 — 정적 측정기 (생성 시 계산, 서버 불필요)

레벨 데이터만으로 계산 가능한 게임별 피처를 뽑아 0~100으로 정규화한다.
각 게임의 `gen()`이 이미 갖고 있는 부산물(솔버 결과 등)을 재활용한다.

| 게임 | 핵심 피처 (이미 있는 것 ✓) | 보조 피처 |
| --- | --- | --- |
| trafficjam | 최단 이동 수 ✓ (BFS) | 탐색 상태 수 ✓, 차 수, 첫 수 선택지 수 |
| watersort | 솔버 해 길이 ✓ (DFS) | 색 수, 초기 "완성 근접도"(같은 색 인접 비율) |
| screwout | 색 큐 인터리브 거리(같은 색 상자 사이 간격) | 판자 수, 커버리지 그래프 깊이, 단계별 선택지 평균 |
| icebreak | 여유 곡괭이 수 ✓ (역수) | 폭탄-보석 인접 쌍 수, 스플래시 마진 합 |
| fillfridge | 조각 수, 큰 조각(2칸+) 비율 | 대안 배치 수(작을수록 어려움, 샘플링 추정) |
| parkmaster | 교차 쌍 수 ✓ | "전원 직진" 시뮬의 최소 근접 거리(작을수록 어려움), 차 수 |
| gaterunner | 그리디 결과/보스 비율 ✓ (마진 역수) | 나쁜-나쁜 문 쌍 수, 속도 |
| picklock | **반응 창(ms)** = 노치 폭 ÷ 각속도 (해석적!) | 핀 수 |
| savedog | (손제작) 잉크 여유율, 틈 수 | 벌 수·속도 |
| pullpin | (손제작) 함정 핀 비율, 필요 순서 깊이 | 배수구 수 |

합성: 피처별로 기준 구간을 [쉬움, 어려움]으로 잡아 0~1 클리핑 후 가중합
→ 0~100. 가중치는 게임별 상수로 시작하고 2층 데이터로 보정한다.
표시: 스테이지 시작 오버레이에 ★~★★★★★ (20점 단위).

### 2층 — 실측 난이도 (익명 집계 텔레메트리)

정적 점수가 맞는지 검증할 실제 데이터. **개인 식별 없이 카운터만** 저장.

- 엔드포인트: `/_stagestat` POST `{game, stage, event: "start"|"clear"|"fail"}`
  - worker: 동일 출처 + JSON 강제 + IP rate limit (기존 관례), vid는 서버가
    읽되 **저장하지 않음** (스팸 방지용 판단에만 사용 가능)
  - DO 저장: `stat:{game}:{stage}` = `{s, c, f}` 카운터 증가만. stage ≤ 500.
  - 클라이언트: records.js 옆에 `_shared/stagestat.js` 한 줄 추가 방식,
    게임은 `blStageStart(n)` / 기존 `blWeeklyReport(n)`(=clear)에 편승
- 조회: GET `/_stagestat?game=x` → 스테이지별 `{s,c,f}` (공개, 캐시 5분)

핵심 지표:
- **클리어율** = c / s (스테이지별)
- **중앙 재시도 수** ≈ s가 클리어 대비 얼마나 부풀었나 (f/c) — 생존 편향에
  더 강건한 체감 난이도 지표
- 주의: 뒤 스테이지 도달자는 고수뿐이라 클리어율이 과대평가됨(생존 편향).
  해석할 때 "같은 스테이지 내 비교"가 아니라 "커브의 기울기"를 본다.

### 캘리브레이션 루프

1. 정적 점수와 실측 (f/c, 클리어율)을 스테이지별로 나란히 그린다
   (admin 페이지에 게임별 난이도 곡선 탭 추가).
2. 목표 커브를 정한다 — 예: 스테이지 1 클리어율 95%+, 5에서 80%,
   10에서 60%, 이후 완만히 하락.
3. 정적 점수가 실측과 어긋나는 게임은 피처 가중치를 조정하고,
   제너레이터의 채택 밴드를 정적 점수 기준으로 교체한다
   (예: parkmaster의 "교차 쌍 수 ≥ n" → "정적 점수 ∈ [스테이지 목표 ± 8]").

## 구현 단계 (제안)

- **Phase 1 — 정적 측정기**: 각 게임 `gen()`에 `difficulty` 필드 추가 +
  시작 오버레이 별점 표시. 서버 변경 없음. 게임당 ~20줄.
- **Phase 2 — 실측 수집**: `/_stagestat` (worker 라우트 + DO 카운터) +
  `_shared/stagestat.js`. 반나절 분량.
- **Phase 3 — 대시보드·보정**: admin에 난이도 곡선 그래프, 목표 커브
  대비 이탈 표시. 이후 가중치·채택 밴드 조정은 데이터 보고 수동으로.

## 리스크 / 비고

- 실측은 트래픽이 적으면 노이즈가 크다 — 스테이지 구간(1-5, 6-10…)으로
  묶어서 보는 폴백 필요.
- picklock처럼 실시간 반응 게임은 정적 측정이 거의 정확하고(반응 창 ms),
  fillfridge처럼 탐색형은 정적 측정이 제일 부정확 — 게임별 신뢰도 라벨을
  달아 대시보드에서 구분한다.
- 텔레메트리는 기존 프라이버시 원칙 유지: IP·UA·vid 미저장, 카운터만.
