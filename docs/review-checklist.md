# Gate 리뷰어 체크리스트

병렬 에이전트가 연 `agent/<서브도메인>/<슬러그>` 브랜치를 **적대적으로** 검증한다.
리뷰어는 구현 에이전트와 대화하지 않고, 브랜치와 diff만 보고 독립적으로 판단한다.

판정은 셋 중 하나이며 **근거 없는 통과는 통과가 아니다** — 각 항목마다
`파일:줄` 또는 실행한 명령과 출력이 있어야 한다.

| 판정 | 뜻 | 오케스트레이터의 행동 |
| --- | --- | --- |
| **통과** | 아래 전부 확인됨, 회귀 근거 없음 | main에 머지 |
| **조건부** | 고칠 게 명확하고 국소적 | 리뷰어 메모를 붙여 구현 에이전트에게 반려 → 재리뷰 |
| **불통과** | 설계가 틀렸거나 회귀가 실재 | 브랜치 폐기 또는 재설계 후 처음부터 |

---

## 0. 기계 검증 (이게 안 되면 나머지는 볼 필요 없다)

리뷰어가 **직접 브랜치를 체크아웃해서 돌린다.** 구현 에이전트의 "통과했다"는
말은 근거가 아니다.

```bash
npm test                      # 617개 기준선 — 줄어들면 안 된다
node _infra/build.mjs         # 에러 없이 dist/ 생성
npm run test:e2e              # 손댄 화면이 SCREENS에 있으면 필수
git diff --stat origin/main   # 소유 밖 파일이 있는지
```

- [ ] 새 기능에 **새 테스트가 붙었다**. 기존 테스트만 도는 브랜치는 조건부다.
- [ ] 테스트가 실제로 실패할 수 있는가 — 로직을 한 줄 뒤집었을 때 빨개지는지
      확인한다(항상 통과하는 테스트는 없는 것보다 나쁘다).
- [ ] `games/avalon/`을 건드렸으면 `_src/avalon/rebuild.sh` 산출물까지 커밋됐다
      (`node _infra/check-avalon-sync.mjs`).
- [ ] 새 퍼블릭 서브도메인이면 `www/index.html` 카드, 비공개면
      `CONFIDENTIAL_SUBDOMAINS` 등록.
- [ ] 주간 기록 게임이면 `_infra/records.js`의 `GAMES`에 dir·범위 등록
      (미등록이면 서버가 제출을 거절한다 — 클라이언트만 보면 안 보이는 버그다).

## 1. 타임존 · 정렬

이 리포는 **KST(Asia/Seoul) 기준**이고 서버는 Cloudflare 엣지(UTC)다. 둘이
어긋나는 지점이 버그다.

- [ ] `new Date()` 로 만든 값을 **날짜 문자열로 자르는 곳**: `toISOString()`은
      UTC라 KST 09시 이전은 전날로 밀린다. `toLocaleDateString("sv-SE", {
      timeZone: "Asia/Seoul" })` 같은 명시적 변환인지 본다.
- [ ] "오늘"·"이번 주"의 경계: 주간 기록은 **월요일 09:00 KST 리셋**이다.
      UTC 자정이나 `getDay()` 로컬 의존이 끼면 사용자 기기 시간대에 따라 결과가
      달라진다.
- [ ] 서버(DO)에서 계산한 경계와 클라이언트에서 계산한 경계가 **같은 함수**를
      쓰는가. 각자 계산하면 반드시 어긋난다.
- [ ] 정렬 키가 문자열인데 숫자처럼 정렬되기를 기대하는 곳
      (`"10" < "9"`), `sort()` 기본 비교자를 숫자 배열에 쓴 곳.
- [ ] 동점(tie) 처리: 같은 점수일 때 순서가 **매 렌더마다 달라지지 않는가**
      (안정 정렬에 의존하면서 키가 없는 경우).
- [ ] 날짜 파싱: `new Date("2026-08-12")`는 UTC 자정, `new Date("2026/08/12")`는
      로컬 자정이다. 섞여 있으면 조건부.

## 2. 저장소 키 충돌 (사용자 간 · 기기 간)

`localStorage`/`sessionStorage`/IndexedDB/DO 스토리지는 **같은 오리진을 모두가
공유한다** — 서브도메인은 경로일 뿐 오리진 분리가 아니다.

- [ ] 새 `localStorage` 키에 **서브도메인·토이 이름 접두사**가 있는가.
      `"score"`, `"settings"`, `"data"` 같은 맨 이름은 다른 토이와 충돌한다.
- [ ] `duri`처럼 두 사람이 쓰는 서비스에서, 키에 **사용자 식별자가 들어가야
      하는데 안 들어간 곳**. 한 기기를 둘이 쓰면 상대 데이터를 덮어쓴다.
- [ ] 반대로 **기기마다 달라지면 안 되는 값**에 기기 로컬 난수 ID를 쓴 곳
      (기기를 바꾸면 기록이 사라진다).
- [ ] DO 스토리지 키가 사용자 입력으로 만들어지는가 — 접두사 없이 이어 붙이면
      `"a"+"bc"` 와 `"ab"+"c"` 가 같은 키가 된다.
- [ ] 기존 키의 **의미를 바꿨는가**(같은 이름, 다른 형식). 이미 그 키를 가진
      사용자가 어떻게 되는지 코드로 확인한다 — 대부분 여기서 조용히 깨진다.

## 3. 스키마 / IndexedDB 버전

- [ ] `indexedDB.open(name, version)`의 **버전을 올리면서 `onupgradeneeded`에
      마이그레이션을 안 쓴 곳**. 기존 사용자는 새 스토어가 없어서 예외가 난다.
- [ ] 반대로 **스토어·인덱스를 추가하면서 버전을 안 올린 곳**. 새 사용자만
      동작하고 기존 사용자는 영원히 옛 스키마다.
- [ ] `onupgradeneeded`가 **여러 버전 점프를 견디는가** (v1 사용자가 v3로
      바로 올라올 때). `switch (event.oldVersion)` fall-through 패턴인지 확인.
- [ ] 저장된 레코드에 **버전/형식 필드**가 있는가. 없으면 다음 변경 때 구분할
      방법이 없다.
- [ ] 서버 블롭(duri·podcast 등)의 형식을 바꿨으면, **옛 형식 레코드를 읽는
      경로**가 남아 있는가. 엣지는 암호블롭을 그대로 중계하므로 서버는
      마이그레이션해 줄 수 없다 — 클라이언트가 둘 다 읽어야 한다.
- [ ] 마이그레이션이 실패했을 때 **기존 데이터를 지우고 새로 시작하지 않는가**
      (`deleteDatabase` 폴백은 데이터 손실이다 — 불통과 사유).

## 4. CSS 우선순위 회귀

- [ ] 새 셀렉터가 **기존 규칙보다 강해서 다른 화면을 덮지 않는가**.
      특히 `_shared/` 의 공용 CSS, 카드 목록(`catalog.css`), 홈 버튼.
- [ ] `!important` 추가 — 거의 항상 조건부다. 왜 필요한지 근거가 없으면 반려.
- [ ] 태그·클래스 셀렉터를 **더 구체적으로 바꾼 변경**: 그 규칙에 의존하던
      다른 요소가 있는지 grep으로 확인했는가.
- [ ] 다크모드: `light-dark()` 를 쓰는가, 하드코딩 색이 끼어들지 않았는가.
      한쪽 모드에서만 읽히는 대비가 없는지 실제로 두 모드 다 본다.
- [ ] 모바일 가로 넘침 — e2e 스모크가 보는 세 가지 중 하나다. 새 화면이면
      `_infra/e2e/smoke.spec.mjs`의 `SCREENS`에 추가했는가.
- [ ] 전역 셀렉터(`*`, `body`, `:root`) 변경은 서브도메인 밖으로 샌다.

## 5. 기존 데이터를 널로 만드는 쓰기 경로

가장 조용하고 가장 비싼 회귀다. **모든 쓰기 경로를 하나씩 따라간다.**

- [ ] 부분 업데이트인데 **객체 전체를 덮어쓰는 곳**:
      `set(key, { a })` 가 기존 `{ a, b }` 의 `b` 를 날린다. 스프레드로
      병합하는지 확인.
- [ ] 로드 실패·파싱 실패 후 **기본값으로 저장하는 경로**. 네트워크가 잠깐
      끊겼을 뿐인데 빈 상태를 디스크에 굳혀 버린다.
- [ ] `undefined`/`NaN`/빈 문자열이 유효값처럼 저장되는가.
      `JSON.stringify({a: undefined})` 는 키를 통째로 버린다.
- [ ] 낙관적 UI: 서버 응답 전에 로컬을 비우고, 실패해도 되돌리지 않는 경로.
- [ ] 두 탭·두 기기가 동시에 쓸 때 **나중 쓰기가 먼저 것을 통째로 덮는가**
      (last-write-wins가 의도된 것인지, 그냥 사고인지).
- [ ] `duri` 싱크: 서버가 ack 후 항목을 버리므로, **ack 시점이 디스크 기록보다
      앞서면 데이터가 영구히 사라진다.** 순서를 코드로 확인한다.
- [ ] 삭제·초기화 버튼의 범위가 의도보다 넓지 않은가
      (`clear()` vs 키 하나 삭제).

## 리뷰어가 지켜야 할 것

- **머지하지 않는다.** 판정만 낸다.
- 구현 에이전트가 쓴 테스트를 **믿지 않는다** — 직접 돌리고, 통과하는 이유가
  로직이 맞아서인지 테스트가 헐거워서인지 본다.
- "괜찮아 보인다"는 근거가 아니다. 각 항목은 확인했거나(파일:줄), 해당 없음이다.
- 위 다섯 부류에 해당 사항이 없으면 **없다고 명시**한다. 침묵은 통과가 아니다.
