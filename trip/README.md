# trip — 여행 계획·예산

trip.bubblelab.dev. 혼자 쓰는 여행 계획·예산 화면이다. **비공개 서브도메인**
(`_infra/build.mjs`의 `CONFIDENTIAL_SUBDOMAINS`) — 랜딩·풀다운·검색 어디에도 나오지
않고 주소를 직접 쳐야 들어온다. 토이가 아니라서 토이 관례(share.js, 주간 기록)는
적용하지 않는다.

**화면에는 로그인이 없다.** estate·lab과 같은 방식이라 주소를 아는 사람은 그냥
들어온다. 다만 계획 탭이 쓰는 **API 는 읽기·쓰기 모두 admin 발급 토큰**을 요구한다
(아래) — 토큰이 없으면 계획 탭은 안내만 뜨고, 실행 탭(일정·예산)은 그대로 쓸 수 있다.
다만 워커가 `no-store` + `X-Robots-Tag: noindex, nofollow`를 붙이고
(`_infra/worker.js`) 방문 집계에서도 빠진다 — 워커의 페이지 집계와
`_shared/engagement.js`의 체류 집계 **양쪽에서** 빼서, 화면이 서버로 보내는 요청이
아예 없다(자기 정적 파일 둘 말고는 네트워크를 쓰지 않는다). 남에게 보이면 곤란한
것(예약번호, 카드번호, 여권번호)은 적지 않는다.

## 저장 위치

**일정·예산**은 브라우저 localStorage(`bl-trip-v1`)에만 있다. 서버로 보내지 않는다
(계획 탭의 가격 관측만 서버에 있다 — 아래). 그래서:

- 기기를 옮기거나 브라우저 데이터를 지우면 사라진다 → 하단 **⬇ 내보내기**로 JSON을
  받아 두고, 새 기기에서 **⬆ 가져오기**로 넣는다(가져오기는 **덮어쓰기**다).
- 폰과 PC가 자동으로 동기화되지 않는다. 한쪽을 원본으로 정해 두는 게 편하다.

## 화면은 계획 / 실행 두 장

| 탭 | 무엇 | 어디에 저장 |
| --- | --- | --- |
| 🔭 계획 | 여행 후보와 그 아래 노선별 가격 관측 (날짜 격자·추이) | **서버**(TripWatchDO) |
| 🧭 실행 | 일정표·예산 | **브라우저**(localStorage) |

경계는 의도한 것이다 — 서버에는 관측 대상(노선·기간 설정)과 "어느 날짜가 얼마였나"가
쌓이고, 내 일정·예산·메모는 올라가지 않는다. 계획 탭 격자에서 칸을 누르면 그 날짜로 실행 탭의
여행이 만들어지는데(항공권 항목·금액 포함), 그 순간부터는 브라우저에만 남는다.

## 계획 탭 — 여행 후보(DestinationWatch)

**관측 대상의 상위 개념은 여행지다.** "몽골"이 가고 싶은 곳이고 ICN→UBN 은 그걸
실현하는 노선 중 하나다 — 둘을 한 덩어리로 두면 홋카이도를 ICN→CTS 와 PUS→CTS 로
함께 비교하거나, 다낭·호이안처럼 항공과 패키지를 같은 여행지 아래 놓을 수 없다.

```
DestinationWatch  몽골 · MN · 2027.06~09 · 5~8박 · 2명 · watching|selected|archived
├─ flights[]   ICN→UBN, PUS→UBN      ← 날짜 격자·관측이 붙는 단위
└─ packages[]  소스·검색어            ← 모델만 있고 수집기는 아직 없다
```

**기간·박수·인원은 여행지에 있다.** 같은 여행을 여러 노선으로 비교하려면 조건이
하나여야 하기 때문이다. 노선마다 구간 × 박수의 모든 (출발일, 귀국일) 조합의 최저가를
관측해 쌓는다. Google Flights 의 날짜 격자와 같은 읽는 법이지만 열을 귀국일 대신
**박수**로 둬서 폰 화면에 들어온다. 관측일별 최저가 추이도 같이 그린다.

저장 키는 노선 id 기준(`obs:<flightId>:…`)이라, 여행지에서 노선을 빼면 그 노선의
관측만 지워진다. 옛 `watch:<id>` 저장본은 첫 접근 때 여행지 아래로 자동 이관되고
노선 id 를 유지하므로 그동안 쌓은 관측이 이어진다.

- **cron 은 6시간마다 조금씩만 갱신한다**(`20 */6 * * *`, 기본 12조합). 한 번에
  그리드 전체를 돌리면 상류 API 쿼터가 하루도 못 간다 — 가장 오래 안 본 조합부터 돈다.
  줄을 세우는 기준은 **가격을 받은 시각이 아니라 조회를 시도한 시각**(`checks:<id>`)이다.
  항공편이 없는 날짜(`no_offer`)는 관측이 남지 않으므로, 관측 시각으로 세우면 그
  조합이 영원히 맨 앞에 남아 매 cron 마다 다시 조회되고 그리드 뒤쪽은 한 번도 못 본다.
- 조합 상한 120개. 넘으면 등록을 거절한다(구간이나 박수 범위를 좁히라고 알려 준다).
- **추이 그래프의 한 점 = 그날 실제로 조회한 것의 최저가**다. 하루에 그리드의 일부만
  도는 구조라, 며칠 전 싼 가격을 오늘 값으로 찍으면 그래프가 거짓말을 한다. 그래서
  점마다 `checked`/`total`(그날 몇 칸을 봤는지)을 함께 저장하고 화면이
  "412,000원 · 34/120 조합 확인"으로 말한다. 하루 안에서는 더 싼 값으로만 내려가되,
  그 바닥을 어제 관측으로 채우지는 않는다. 당일 점은 **누적 통계**라, 아침에 찾고
  저녁에 no_offer 가 되어도 그날 found 는 1로 남는다(`checks` 의 `foundAt` 기준) —
  그러지 않으면 "가격을 하나도 못 찾았는데 최저가 41.2만"처럼 읽힌다. 가격을 하나도 못 받은 날은 `min: null`
  점으로 남는다 — "그날 얼마인지 모른다"와 "그날 안 봤다"는 다른 이야기다.
- 격자 칸은 **마지막으로 본 값**이라 며칠 전 값일 수 있다. 칸 툴팁과 요약에 "오늘/
  어제/N일 전 관측"을 함께 띄운다.
- **읽기·쓰기 모두 admin 이 발급한 토큰**이 필요하다. 응답에는 가격뿐 아니라
  여행지·기간·인원·노선이 함께 들어 있어 공개하면 **여행 의향**이 읽히고, 혼자 쓰는
  화면이라 공개 조회로 얻는 이익이 없다. 쓰기를 막는 이유는 하나 더 있다 — 남이
  노선을 만들어 상류 API 쿼터를 태울 수 있다.
  발급: admin → `POST /api/trip/token` → 계획 탭 🔑 에 붙여 넣기(브라우저에 저장).
  데몬 push 만 별도 secret(`TRIP_SINK_SECRET`)이라 화면 토큰이 새도 분리돼 있다.

### 가격의 성격 — 이 구분이 제일 중요하다

관측마다 `quality` 를 같이 저장하고 화면이 배지로 나눈다. 하나라도 낮은 게 섞이면
배지를 낮춰 단다.

| quality | 뜻 |
| --- | --- |
| `reference` | 참고 시세(캐시·집계·목업). 그대로 결제되는 값이 아니다 |
| `live` | 그 시점 실제 판매 화면/검색 결과의 값. **예약 직전 재확인 필요** |
| `verified` | 결제 직전까지 눌러 좌석·최종가를 확인한 값 (아직 아무도 못 만든다) |

**"예매가(bookable)"라고 부르지 않는다.** 검색 결과 가격은 좌석 재고·수수료 때문에
결제 화면에서 바뀔 수 있어서, live 를 bookable 로 부르면 그 금액 그대로 살 수 있다고
오해한다. Amadeus 도 Search → Price → Create Orders 순서를 명시하고, 우리는 아직
Price 단계를 부르지 않는다.

| 프로바이더 (`TRIP_FLIGHT_PROVIDER`) | 예매가? | 메모 |
| --- | --- | --- |
| `sink` | live | 집 PC 데몬이 실제 판매 화면에서 받아 `/_trip/snapshot` 으로 push. **평소 경로** |
| `amadeus` + `AMADEUS_ENV=production` | live | Flight Offers Search 의 `grandTotal`. 키가 있을 때만 |
| `amadeus` + 테스트 환경 | reference | 제한된 캐시 데이터 |
| `mock` (자격증명이 없을 때 기본) | reference | 로컬 개발용 가짜 가격 |

> ⚠️ **Amadeus Self-Service 는 종료됐다.** 예전처럼 가입해서 키를 즉시 받는 흐름이
> 신규 사용자에게는 열려 있지 않고, 지금은 Enterprise 문의 기반이다 — 이 프로젝트
> 규모에는 과하다. 코드의 amadeus 경로는 **키가 생기면 쓰는 자리**로만 남겨 둔다.
> 지금 프로덕션은 자격증명이 없어 `mock`(참고가)으로 돌고 있다.

그리고 Amadeus 는 애초에 LCC 와 일부 대형 항공사를 빼고 published GDS fare 중심이라,
"한국 소비자가 실제로 싸게 사는 가격"을 온전히 잡지 못한다. **평소 경로는 집 PC
데몬(`sink`)** 이 맞다 — 네이버 항공권·구글 플라이트 같은 실제 구매 창구를 보고
아래 payload 를 밀어 넣으면 된다.

> ⚠️ **집 PC 데몬(`_src/trip-sink/`)은 아직 만들지 않았다.** 서버 쪽 입구
> (`POST /_trip/snapshot`, `Bearer TRIP_SINK_SECRET`)와 저장·집계·교정 도구는
> 준비돼 있어, 지금도 curl 로 밀어 넣으면 그대로 쌓인다.

Payload 는 두 경로가 같다:

```json
{ "flightId": "f...", "observations": [
  { "depart": "2026-09-10", "ret": "2026-09-17", "price": 812300,
    "currency": "KRW", "carrier": "OM", "stops": 0, "bookable": true, "source": "..." },
  { "depart": "2026-09-11", "ret": "2026-09-18", "status": "no_offer" }
] }
```

`status` 는 `found` · `no_offer` · `error` 셋이고, 생략하면 가격 유무로 정해진다.
**가격이 없어도 항목을 보내는 편이 낫다** — 조회했다는 사실이 남아야 다음 회차가
그 조합을 건너뛰고 앞으로 나간다.

## 실행 탭

- **일정 탭** — 여행 기간이 날짜 카드로 펼쳐진다. 항목은 시간·내용·분류·금액·
  상태(계획/예약/결제)·메모. 항목을 누르면 그 자리에서 편집되고, 추가 후에는 빈 폼이
  다시 열려 연달아 넣을 수 있다.
  - 날짜를 비워 두면 맨 아래 **"날짜 미정"** 카드로 모인다(항공권처럼 금액만 먼저
    잡아 두는 경우). 기간 밖으로 밀려난 항목도 여기로 내려올 뿐 지워지지 않는다.
  - **총액에는 날짜 미정·기간 밖 항목도 들어간다** — 빠지면 예산이 거짓말이 된다.
- **예산 탭** — 분류(항공·숙소·교통·식비·관광·쇼핑·기타)마다 예산을 넣으면 계획액과
  비교해 막대·초과액이 나온다. 합계 줄에 1인당·하루당이 같이 뜬다.
- 통계 줄: D-day · 계획 총액 · 예산 잔액 · 결제 완료.

## 금액과 환율

금액은 **항상 원(KRW) 정수로 집계**한다. 항목은 원/현지통화 중 하나로 입력하고,
현지통화는 여행마다 하나뿐인 환율(⚙️ 설정, 현지 1단위 = ?원)로 환산된다. 항목마다
환율을 두지 않는 건 의도한 것 — 환율을 고쳤을 때 과거 항목이 따라오지 않으면 계획
단계에서 더 헷갈린다. 계획용 어림값이지 회계 장부가 아니다.

`1인당 금액` 체크를 켜면 그 항목만 인원수만큼 곱해진다(식비·입장료).

## 구조

| 파일 | 역할 |
| --- | --- |
| `index.html` | 화면 전부 (바닐라, 의존성 없음) |
| `budget.js` | 순수 계산 — 환산·집계·기간·저장본 정규화 |
| `_infra/trip-flights.js` | 여행지·노선 모델 검증, 프로바이더(amadeus·sink·mock), 집계 |
| `_infra/trip-watch.js` | TripWatchDO — 여행지 저장·관측·조회 이력·추이·cron 갱신 |
| `_infra/worker.js` | `/_trip/*` 라우팅과 토큰 게이트 |

**계산은 `budget.js` 밖으로 새지 않게 한다.** 화면과 `_infra/trip.test.mjs`가 같은
모듈을 쓰기 때문에, 합계를 index.html 안에서 따로 더하기 시작하면 테스트가 못 보고
언젠가 두 숫자가 어긋난다.

저장본은 읽을 때 `normalizeStore`가 **거절하지 않고 고친다** — 남의 파일이 아니라 내
옛 저장본을 여는 쪽이라, 모르는 필드는 버리고 이상한 값은 기본값으로 끌어내린다
(환율 0 → 1, 인원 0 → 1, 모르는 분류 → 기타). 거절하면 기록만 잃는다.

## 패키지 관측 (PackageWatch v0)

여행지마다 여행사 패키지 상품을 같이 쌓는다. 몽골처럼 **자유여행이 항공+숙소로 끝나지
않는 곳**(테를지·초원 이동에 차량·기사·가이드·게르가 붙는다)에서는 패키지와의 비교가
곧 이 화면의 존재 이유다.

### 표시가만 저장하지 않는다

"749,900원" 상품이라도 실제로는 가이드 경비, 필수 선택관광, 기사팁, 현지 결제가 붙는다.
표시가만 쌓으면 나중에 자유여행과 비교할 때 패키지가 실제보다 싸 보인다.

| 필드 | 뜻 |
| --- | --- |
| `listedPrice` | 광고된 1인가 |
| `mandatoryLocalFee` · `knownMandatoryOptions` | 금액을 아는 필수비용 |
| `effectivePrice` | listedPrice + 아는 필수비용 |
| `unknownCosts[]` | 있는 건 아는데 금액을 모르는 것 (예: 선택관광, 기사팁) |
| `floor` | `unknownCosts` 가 있으면 true — effectivePrice 는 **하한**이다 |
| `tags[]` | 노쇼핑·출발확정·게르2인실 등. 가격만큼 중요하다 — 싼 여행과 가성비 좋은 여행은 다르다 |

**모르는 값을 0원으로 채우지 않는다.** 화면은 `1,189,000원~/인` 처럼 물결과
"추가비용 확인 필요" 배지로 하한임을 밝힌다. 최저가 정렬도 표시가가 아니라
`effectivePrice` 기준이다 — 표시가로 줄 세우면 현지경비를 감춘 상품이 항상 이긴다.

가격 변화는 **같은 상품의 직전 관측**과 비교한다(상품마다 `previous` 를 들고 있다).
더 싼 상품이 새로 뜬 것과 값이 내린 것은 다른 이야기다.

### 수집 — 파서는 저장된 페이지로 교정한다

여행사 사이트는 우리 배포 밖이고 구조가 자주 바뀐다. 그래서 셀렉터를 짐작해 넣지 않고
**표준 구조부터** 읽는다: ① JSON-LD(schema.org Product/Offer) ② 페이지에 심긴 상태
JSON(`__NEXT_DATA__` 등) ③ 둘 다 없으면 **실패로 남긴다** — 억지로 정규식을 긁어 잘못된
숫자를 저장하는 것보다 "못 읽었다"가 낫다.

**목록 페이지만으로는 수집을 시작하면 안 된다.** 거기에는 표시가와 제목뿐이고
출발일·현지 필수경비·선택관광은 **상품 상세(또는 출발일 선택) 페이지**에 있다.
목록에서 읽은 상품은 파서가 `unknownCosts: ["현지 필수경비","선택관광"]` 로 표시해
실질가를 하한으로 남긴다 — 0원으로 삼키지 않기 위해서다.

CLI 는 마지막에 **사람이 원문과 대조할 다섯 가지**를 체크리스트로 찍는다:
상품명 · 1인 표시가 · 출발일 · 알려진 필수 현지비용 · 모르는 비용을 0원으로 삼키지
않았는지. 다섯 개가 모두 ✓ 여야 cron 수집을 시작한다.

```bash
# 실제 상품 상세 페이지를 저장한 뒤
node _infra/trip-package-parse.mjs mongolia.html --source modetour --destination <destId>
node _infra/trip-package-parse.mjs mongolia.html --destination <destId> --json \
  | curl -X POST https://trip.bubblelab.dev/_trip/snapshot \
      -H "Authorization: Bearer $TRIP_SINK_SECRET" -H 'Content-Type: application/json' -d @-
```

> ⚠️ **첫 소스(모두투어)의 셀렉터는 실제 페이지로 검증되지 않았다.** 이 저장소를 만든
> 환경에서 여행사 사이트로 나가는 네트워크가 막혀 있어 실제 HTML 을 확인하지 못했다.
> 위 CLI 로 한 번 교정한 뒤에 수집을 시작해야 한다. 목록 페이지에서는 표시가만 읽히므로,
> 현지 필수경비·선택관광은 상세 페이지를 봐야 하고 그전까지 effectivePrice 는 하한이다.

여행사는 **하나만** 붙인다. parser 와 snapshot 의미를 한 사이트로 안정화한 뒤
provider 를 복제하는 편이, 여러 곳을 동시에 열고 전부 어중간하게 두는 것보다 낫다.
